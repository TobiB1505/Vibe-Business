# Sprint 0065 — ADR 0042 §P3: wiring the repair trigger, for both caches

Status: **Implemented and tested against `FakeDatabase`. No migration — a TypeScript-only change.** All five RPC primitives and their marker columns were already deployed (Sprint B0/B1); this sprint only adds callers.

## The gap this closes

ADR 0042 §P3's own "Shape of the change" table names the repair trigger's location as "`getBillingBalance` (`service.ts`) **and the lot-level equivalent**" — as if both already existed. Sprint C wired the account side; Sprint D wired two of the lot-side hot-path writers but explicitly left the trigger itself unscoped, naming the exact gap: "unlike the account side there is no existing 'lot balance read' to attach a gated `BILLING_REPAIR_ENABLED` call to... `reconcileLotAllocation` still has zero callers outside its own test." This sprint closes that, and — per explicit instruction after the research below surfaced it — a second gap alongside it.

## What was found before anything was wired

Traced directly, not assumed: **`getBillingBalance`, the account-side repair trigger Sprint C built, has zero production callers.** The real billing page (`src/app/app/billing/page.tsx`) calls `getBillingOverview` (`billing/overview.ts`), which never reads `account.postedCredits`/`reservedCredits` at all — every customer-facing balance figure and every spend-admission check (`getBillingOverview`, `getHeaderCreditBalance`, `availableSpendableCredits`) computes from lots via `spendableCapacity`, never from the account cache. So even with `BILLING_REPAIR_ENABLED=true`, account-side repair could never have fired in production — a real, previously undocumented defect, confirmed by grep (zero non-definition callers) and by reading `overview.ts` directly. Asked and answered this session: fix both gaps together rather than wire the lot side onto the same unreachable pattern.

Also established before writing any code: lot drift is proven one-directional by the ADR itself (`allocated_credit_units` can only be too *high*, from an unreturned capacity return, never too low), so it can only *understate* what `spendableCapacity` reports a customer can spend — a customer-negative bug, never a billing-safety risk. This is why the chosen attachment point matters: `getBillingOverview` (the one deliberate balance read), not `getHeaderCreditBalance` (renders on every page, and its own docblock already states a "must not pull a ledger history" constraint that a reconcile+repair scan would violate) and not `availableSpendableCredits` (the latency-sensitive pre-operation admission gate, where a correctness case for inline repair does not exist given the drift direction proven above).

## What shipped

**`AuditEventType` gains `credit_drift.detected`/`repaired`/`repair_failed`** (`audit-log/events.ts`) — named in ADR 0042's own "Audit trail" section from the start, never implemented until now: `getBillingBalance` only ever logged via `console.error`, and neither it nor `repairAccountBalance` called `recordAuditEvent`. Account-level (no `projectId`), so structurally excluded from every project-scoped activity feed — confirmed by reading each feed's own query, all of which filter `.eq`/`.in` on `project_id`, which never matches a `NULL` row.

**`reconcileAndRepairBalance`** (`credits/service.ts`) — extracted from `getBillingBalance`'s existing detect/log/gate/repair/re-check body, now also posting the three audit events and, a real behavior fix bundled with the extraction: catching a `repairAccountBalance` RPC failure instead of letting it propagate uncaught out of the caller. `getBillingBalance` becomes a thin wrapper around it; its exported signature and behavior are unchanged for existing callers.

**`listAllocationsForGrants`** and **`repairLotAllocation`** (`credits/lot-store.ts`) — a new batched query (allocation rows grouped by `grant_id`, one round trip for however many active lots an account holds) and a thin `.rpc()` wrapper onto `repair_lot_allocation`, mirroring `repairAccountBalance` exactly. The RPC's fake mirror (`fakeRepairLotAllocation`) already existed in `operations/test-support.ts`, built in Sprint C in anticipation of this wiring and unused since.

**`reconcileAndRepairLotAllocations`** (`credits/lot-store.ts`) — the lot-side counterpart to `reconcileAndRepairBalance`, looping an account's active lots, auditing and (gated) repairing each independently so one lot's repair failure cannot block another's, and returning the lots array with any repaired figure corrected in place.

**`getBillingOverview` wires both** (`billing/overview.ts`) — fetches `reservations` (not fetched before) and, once lots are loaded, their allocation rows, then runs both reconciliations concurrently. Only the lot result is consumed further: `spendableCapacity` is computed from `reconcileAndRepairLotAllocations`'s corrected lots, so a repair this same call makes is reflected in `availableCredits` immediately. The account-side call is a deliberate side effect — its corrected figures are never rendered by this page, so nothing beyond the audit trail and the underlying row consumes its return value. `getHeaderCreditBalance` is untouched, on purpose: it stays correct passively, since a repair fired from `getBillingOverview` is a database write every subsequent reader — including the header's next call — already sees.

## Tests

`credits/lot-store.test.ts` gains three new `describe` blocks: `listAllocationsForGrants` (grouping across multiple lots, an empty-allocations lot correctly absent from the map, an empty grant-id list); `repairLotAllocation` (a clean no-op call, an unrecognized RPC failure propagated — reusing the file's existing `rpcAlwaysErrors` fixture, hoisted to file scope for reuse); `reconcileAndRepairLotAllocations` (no-op when consistent; detects and audits without repairing while the flag is unset; repairs and audits when set — proven by simulating a crash between an allocation's status flip and its materialize call, the same technique `store.test.ts`'s account-side self-heal test uses; audits `repair_failed` and keeps the unrepaired figure when the RPC throws; repairs only the drifted lot when an account holds several).

`credits/service.test.ts` gains a `reconcileAndRepairBalance` block mirroring the lot-side tests exactly in shape: no-op, detect-without-repair, repair-and-audit, repair-failure-caught-and-audited — the last one is the test that would have caught today's uncaught-throw defect, and its prior absence is exactly the gap this sprint's audit-trail work closes.

`billing/overview.test.ts` (new file) proves the gate from the outside, not just internally: `getBillingOverview`'s `availableCredits` reflects a repaired lot's capacity within the same call when the flag is set, and is computed from the unrepaired, understated figure when it is unset; a combined test proves the account-side repair fires as a documented side effect (drift events posted, the account row corrected) even though the page's own return value never surfaces it. `getHeaderCreditBalance` is proven **not** to trigger repair — reading the drifted figure even with the flag set — followed by a test proving it reads the *corrected* figure passively once a prior `getBillingOverview` call has already repaired the underlying row.

`audit-log/view.test.ts` gains one test: `credit_drift.repair_failed` is explicitly mapped to "problem" tone (its name does not end in `.failed`, so the file's own suffix heuristic would otherwise default it to "neutral"), and `credit_drift.repaired` to "success".

**Two real fixture bugs found and fixed while writing these tests, not worked around**: `heldAgainstLot` (`lot-store.test.ts`, pre-existing) never returned the lot id it created, silently defaulting to `undefined` when a new test destructured `lotId` from it — caught immediately by every assertion showing 100% drift on a lot that should have been consistent. And `accountWithLot`'s own `lotId` (also pre-existing) is only reliable for an account's *first* lot — calling it a second time against an account that already holds one returns `listActiveLots()[0].id`, not necessarily the lot just granted, since two lots created in the same test can tie on `granted_at`. Both were pre-existing helpers never previously exercised with more than one lot per account; fixed by returning `lotId` from `heldAgainstLot` (additive, no existing caller affected) and by finding a second lot's id by exclusion in the new tests that need one, rather than changing `accountWithLot`'s contract.

Full suite: **6,091 tests** (6,071 + 20 new), lint 0 errors, typecheck clean, build green.

## What this does not do

**No migration.** All five RPC primitives and their marker columns were already deployed; `audit_events.event_type` is unconstrained `text`. **No activation** — `BILLING_REPAIR_ENABLED` stays unset; while unset every new call site behaves exactly as `getBillingBalance` already did (drift detected and now audited, `repair_*` never reached), so this sprint changes no customer-visible behavior on its own. Sprint F remains untouched. **No change to `reconcileBalance`, `reconcileLotAllocation`, or any of the five SQL primitives** — all reused exactly as already built and already proven under real Postgres (Sprint B1). **`getHeaderCreditBalance`/`availableSpendableCredits` are deliberately left unrepaired-on-read**, named with reasoning in the architecture plan and reaffirmed by this sprint's own tests, not silently skipped.
