# Sprint 0067 — ADR 0041 §P3: recording drift authority, derived and found absent

Status: **Implemented. No migration, no production code change — derivation and documentation only.** No new SQL function, no new column, no change to `settleReservation`, `settleReservationAllocations`, `decideSettlement`, or `settleOperationCredits`.

## The gap this closes

Sprint 0066 named **recording drift** — whether an allocation row's own `consumed_units` correctly reflects what its reservation was actually charged, per the ledger's `charge` entry and per `billing_credit_reservations.settled_credits` — as an explicit non-goal, without tracing whether it can actually occur. Explicit instruction for this sprint: derive the authority relationship between Reservation, Allocation, and Ledger for this specific question, from the current code, with proofs — architecture and documentation only, no implementation.

## What the derivation found

Three parallel research passes traced `settleReservation` (`service.ts`), `settleReservationAllocations` (`lot-store.ts`), `decideSettlement` (`balance.ts`), every production call site, and every crash-and-retry window between them:

- **All three writes derive from one variable, read once.** `settleOperationCredits` is the sole production caller of both settlement functions; it reads `reservation.reservedCredits` exactly once and passes the identical value to each. `decideSettlement` sets the ledger's `credit_delta` to exactly `-actualCredits` with no independent recalculation. Every billed operation family routes through this one function with no amount parameter of its own. `consumed_units`'s sum, the ledger charge, and `settled_credits` are the same number today because there is exactly one caller and it reads its source once — not because anything enforces agreement between the three tables.
- **No table can arbitrate another, structurally.** No constraint or query anywhere (besides Sprint 0066's own new test) compares the allocations' summed `consumed_units` against `settled_credits`. The ledger has no `allocation_id`/`grant_id` column in any migration and cannot be joined to a specific lot's allocations except through the unconstrained `reservation_id` column both tables happen to carry.
- **Every traced retry path preserves identity rather than re-deriving it, and neither settlement function is idempotent against a *changed* input, only a *repeated* one.** A crash between allocations settling and the ledger charge posting recovers correctly (allocations no-op on retry, ledger + reservation close normally). A crash between the ledger charge posting and the reservation closing recovers via the existing-charge branch — the Sprint 0057 E1 fix. But neither retry path compares a second call's `actualCredits` to what is already recorded: both functions silently discard it. This is a real gap in the primitives, currently unreachable only because no production caller ever supplies a differing value.
- **`refundCharge` (`service.ts:756`) is the one concrete, traced mechanism that would break the invariant.** It has zero callers anywhere in the repository — dormant, not active — and its body never touches allocations or the reservation row. If ever wired up, it would split the ledger's net picture from the allocations' fixed `consumed_units` with nothing to reconcile them.

**The decision this produced**: the question as posed — which of Reservation, Allocation, Ledger is authoritative over the others — does not have a winner, because there is no conflict for one to resolve. All three values agree today by call-site accident (one caller, one read), not by enforcement. No repair mechanism is proposed, because nothing traced shows drift occurring. This is different in kind from Sprint 0066's lot-repair finding: that sprint confirmed a real mechanism (`repair_lot_allocation`) was correctly scoped and proved a genuine, previously-unproven concurrency property under real Postgres. This sprint finds no mechanism is warranted at all — the invariant is not currently violable through any traced production code path — and records the two specific preconditions (silent-discard on a changed retry amount; `refundCharge`'s dormancy) that a future sprint would need to close before either could become a real source of drift.

## What shipped

**ADR 0041 revised in place**, seventh revision, per rule 83 — a new §P3 subsection, "Recording Drift Authority," carrying the full derivation above (the single-variable mechanism, the structural absence of cross-table arbitration, the crash-window trace, the two named preconditions), plus a revision notice at the top matching the document's own established style. Nothing in P1, P2, P4, the account-side steady-state design, or the Lot Repair Authority subsection is reopened.

**No test, no code, no migration.** Unlike Sprint 0066, this sprint does not add a concurrency test or a `FakeDatabase` invariant test, because it does not establish a new property that needs pinning — Sprint 0066's own new test (`operation-billing.test.ts`, "keeps an allocation's settled sum equal to the reservation's own settled figure") already documents the one property this derivation depends on, and no new mechanism exists here to test.

## What this does not do

**No production code change.** `settleReservation`, `settleReservationAllocations`, `decideSettlement`, and `settleOperationCredits` are all confirmed, by trace, to produce identical values across allocations/ledger/reservation for every call site that exists today; none is modified. **No repair mechanism** — there is nothing traced to repair. **No decision to wire up `refundCharge`** — it remains dead code; this sprint only names what its activation would require alongside it. **No new constraint, trigger, or cross-table check** — adding one now would enforce an invariant against a caller shape that does not exist. **No migration. No activation** — `BILLING_REPAIR_ENABLED` stays unset, Sprint F untouched, per standing instruction.
