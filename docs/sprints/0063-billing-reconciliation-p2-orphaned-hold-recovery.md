# Sprint 0063 — ADR 0041 §P2: orphaned hold recovery

Status: **Migration deployed and verified against real Postgres; the application code is TypeScript-only and reaches production through the normal PR/merge/Vercel deploy path.** One additive migration (`operation_runs.pause_cycle`), applied via the Supabase MCP's `apply_migration` — never the SQL Editor rule 29 forbids — and verified by independent read-back rather than trusting the call's own success response: the column exists (`smallint not null default 0`), all 136 pre-existing rows backfilled to `0` by the column default, and the migration recorded in the remote history as `20260823134718_operation_pause_cycle`, the 57th migration matching the 57th local file exactly. A purely additive single-column change with no new function, policy or grant, so no `get_advisors` pass was run — nothing security-relevant changed for it to find.

## The architecture plan, and one finding that changed its scope mid-implementation

Full mapping, state transitions and the four orphan states identified are in the approved plan (reproduced in full in this sprint's commit history). One finding surfaced only while implementing §P2's needs_user resolution and materially changed what shipped for `agent_execution`: traced directly against the actual code, **no path in this repository transitions an agent run out of `needs_user_input` after its interrupt is answered** — `answerExecutionInterrupt` (`coding-agent/store.ts`) only marks the interrupt row; nothing calls `startAgentExecution` again, nothing requeues the operation, nothing flips `agent_execution_runs.status` back. This is a genuine, separate gap, larger than this sprint, not something ADR 0041 assumed away — it means "release-on-pause, re-reserve-on-resume" for `agent_execution` can only ever be "release-on-pause": there is no resume event to hook a re-acquire to yet.

## What shipped

**A generalized staleness sweep** (`src/modules/operations/staleness.ts`, new) — `expireStaleOperation`, the same "declare stale only at a read that already exists" shape `expireStaleAgentExecution` already proved, applied to `business_audit`, `opportunity_generation` and `action_planning`. Wired into `getOperationStatus` (`service.ts`), mirroring exactly how `getAgentExecutionStatus` wires in its own version. The deadline per operation type is that operation's own measured AI-call `timeoutMs` (`modules/ai/operations.ts`) plus a shared 5-minute grace — reused, not reinvented, and the grace covers network/scheduling overhead rather than call variance the timeout already accounts for. `agent_execution` and every never-billed operation type are deliberate no-ops: the deadline map has no entry for them, so the function returns immediately rather than racing `agent_execution`'s own, more precise mechanism.

**Release-on-pause, everywhere a pause exists.** `pauseOperationForUser` (`operations/store.ts`) now increments a new `pause_cycle` counter inside its own existing guarded UPDATE — no new race, since the status guard already ensures at most one caller's write ever lands — and reports it back. Both call sites release the hold immediately, with the reason resolved per call site exactly as ADR 0041 specifies: `business-audit/execution.ts`'s `checkFounderQuestionStep` releases `cancelled_before_usage` (no inference has run yet when this specific pause fires); `agent-execution/execution.ts`'s `startAgentStep` releases `abandoned_with_usage` (real inference already ran to reach the interrupt).

**Re-acquire on resume — `business_audit` only.** The natural hook is not where a first read suggested: `prepareEvidenceStep`'s existing `operationHasCreditHold` check only ever runs once per operation, short-circuited by `resultId` on every later re-entry including a resume. The real spend happens in `runInferenceStep`, which had no hold check of any kind before this sprint. It now verifies the hold before the paid call when the audit is credits-funded, and re-acquires one if a pause released it — keyed by `` `operation:<id>:resume:<pauseCycle>` ``, not the bare operation id, because the bare key would replay the first (now released) reservation instead of taking a fresh one. Confirmed as a real gap before fixing it: without this, a resumed credits-funded audit would spend real provider money and then silently settle nothing, because `settleOperationBilling` no-ops on a non-active reservation rather than erroring.

**Two small, backward-compatible seam extensions**, both additive optional parameters: `holdOperationCredits` accepts an `idempotencyKey` override (defaults to today's `operation:<id>` for all four existing callers), and `releaseOperationBilling` accepts a `reason` override (defaults to its existing `providerUsageOccurred`-derived boolean for its existing callers). Both exist because the family-specific calls this sprint adds need a third value neither existing two-state mapping expressed.

## Tests

`staleness.test.ts` (new): each of the three covered operation types fails and releases past its deadline; each is left alone inside it; `needs_user` is never touched regardless of age (it is not a staleness question at all); `queued` is never touched (may not have been picked up yet); `agent_execution` and a never-billed type are both no-ops; repeated calls repair once. `service.test.ts` gains one wiring-proof test. `business-audit/execution.test.ts` gains a `pause and resume` block: releasing on pause, not re-pausing for an already-asked question, re-acquiring a distinct active reservation on resume, settling the audit against the re-acquired hold, and not double-acquiring on a retried resume step for the same cycle — the last four required constructing a genuine `ask: true` fixture (an unconfirmed AI-inferred audience with a prior audit's matching lens assessment, the same recipe `needs-user.test.ts` uses), not a mocked decision. `agent-execution/execution.test.ts` gains one test proving the release fires with `abandoned_with_usage` for a funded, paused run, with its docblock stating the no-resume boundary explicitly rather than leaving it implicit.

One fixture gap found and fixed, not worked around: `FakeDatabase.seed()` does not apply column defaults the way a real INSERT does (unlike `FakeQuery`'s own insert path, which already carries this pattern for other columns), so every direct `operation_runs` seed needed an explicit `pause_cycle: 0` once `pauseOperationForUser` started reading it.

Full suite: **6,055 tests, lint 0 errors, typecheck clean, build green.**

## What this does not do

`agent_execution`'s `needs_user_input` state is not resumable by this sprint or any prior one; building that is out of scope here and left as an explicit, newly-documented gap rather than a silent one. A narrow residual window remains even for `business_audit`: a crash between `requeueAnsweredOperation` succeeding and the re-acquire completing leaves the operation `queued` with no valid hold and nothing sweeping `queued` operations (deliberately, for the same reason `expireStaleAgentExecution` never sweeps `queued` either) — named in the plan as an accepted gap, not closed here. No lot-side repair, no Sprint F activation — both explicitly out of scope per instruction.
