# Sprint 0069 — closing the residual real-Postgres constraint gaps

Status: **Two of four residuals closed; one corrected and partially closed; one investigated and left open, for a documented reason.** Code changes are test/CI infrastructure only — no production behavior change.

## The gap this closes

`docs/ROADMAP.md`'s "No test exercises a real Postgres constraint" entry named four things Sprint 0057 E2/E2b's real-Postgres concurrency suite still did not prove: the local CI stack has no Supavisor and no network latency, so it is not the deployed topology; twenty iterations miss a 5% race 36% of the time; `CONTENTION_ATTEMPTS = 10` is not shown to be minimal, because the round count is not observable from outside `admitHold`; and the gate is path-filtered, so a change elsewhere that breaks it is not caught. Four parallel research passes investigated each before any code changed.

## What each investigation found, and what shipped

**Iteration count — closed.** `harness.ts`'s own `ITERATIONS` docblock already stated the exact math: `(1-p)^n` miss probability, twenty misses a 5% race 36% of the time. Solving for the smallest `n` that drives that under 5% gives 60 (`(0.95)^60 ≈ 4.6%`). Estimated CI cost, scaling linearly from Sprint 0057 E2b's own measured per-iteration timing: roughly 5-6 minutes total job time, comfortably inside the 30-minute timeout. `ITERATIONS` raised to 60, the pinned assertion in `configured.concurrency.ts` updated to match, and every comment across the suite that stated "twenty" as a live fact (not a historical observation) corrected — including one in `holds.concurrency.ts` that had gone stale for an unrelated reason (see below). Named explicitly, not implied away: sixty is still not proof of absence for genuinely rare races — a 1% race is still missed 54.7% of the time at sixty repetitions.

**Path filter — closed.** Tracing every production call site that reaches `postLedgerEntry`/`claimReservation`/`allocateReservation`/`reconcileAndRepair*` found three real gaps outside the filter's three directories (`src/modules/credits/**`, `src/modules/operations/**`, `src/modules/coding-agent/**`): `src/modules/billing/webhook-service.ts`'s Stripe-funded `grantCreditLot` calls, `src/modules/billing/overview.ts`'s `getBillingOverview` live-repair calls, and `ensureWelcomeGrant` calls from two `src/app/app/**` server-action directories. `.github/workflows/concurrency.yml`'s `paths:` list widened to include `src/modules/billing/**`, `src/app/app/billing/**`, and `src/app/app/connect/github/repositories/**`. ADR 0040 revised in place (first revision, rule 83) — a dated notice plus an updated §7, both explicit this is a widening of an already-accepted filter's boundary, not a reversal of the filtering decision or its cost reasoning.

**`CONTENTION_ATTEMPTS` — premise corrected, observability closed, minimality not.** The investigation's most consequential finding: `admitHold` — the function every prior mention of this gap (Sprint 0057 E2b's own record, `contention.ts`'s docblock, `holds.concurrency.ts`'s comments) names as the unobservable one — no longer contains a compare-and-swap retry loop at all. ADR 0042's account-side hot-path conversion (Sprint C, shipped the same day this gap was named) replaced it with a single row-locked `.rpc()` call. `CONTENTION_ATTEMPTS` now bounds exactly two live loops, both in `lot-store.ts`: `takeFromLot` and `returnToLot`. Every place that stated the old framing as current fact is corrected: `holds.concurrency.ts`'s wall-clock-reporting comment, `contention.ts` is unchanged (its own docblock already discusses the constant generically), and this ADR/ROADMAP text.

Made the round count observable without changing production behavior: `allocateReservation` gained an optional `onContentionRound?: (fn, attempt) => void` field, threaded into `takeFromLot`/`returnToLot`, defaulting to nothing and never passed by any production caller. `allocation.concurrency.ts` (Class C — the one existing real-Postgres test that actually collides two callers on `takeFromLot`'s CAS write) now records the peak round count either racer needed per iteration and reports min/max/mean plus headroom against `CONTENTION_ATTEMPTS`, mirroring Class A's existing "reported, not asserted" wall-clock pattern rather than inventing a new one. **What this does not do**: determine whether 10 is actually minimal. That requires reading this report from a real run against real Postgres — this environment has none configured, confirmed the same way every prior sprint touching this suite has confirmed it (the suite loads and skips cleanly; `configured.concurrency.ts`'s own unskippable guard fails loudly as designed). The observability half of the gap is closed; the measurement itself is a next CI run's finding, not this sprint's.

**Supavisor and network-latency topology parity — investigated, left open, for a stated reason.** Two findings foreclose a naive attempt at either, rather than leaving the gap merely unexamined:

- Decompiling the pinned Supabase CLI's own service-registry code found `postgrest`'s `PGRST_DB_URI` is wired directly to the `db` (Postgres) container's hostname in every code path — never to Supavisor — in this CLI version. Enabling `[db.pooler]` locally and un-excluding `supavisor` from the workflow's `-x` list would start a fifth container that sits *beside* the tested path (`application → supabase-js → PostgREST → PostgreSQL`), not *in* it. Actually routing PostgREST's own backend connection through the pooler isn't a config flip this CLI version exposes.
- Network-latency simulation (`tc netem`) is technically available on a GitHub-hosted runner, but a naive implementation shapes the wrong hops — production's real latency lives on the client→edge hop, not the container-to-container hops inside one Docker network — and directly contradicts the suite's own stated design: `harness.ts`'s docblock is explicit that "there is no retry and no tolerance threshold anywhere in this suite; one safety violation... is a defect, not noise," and injecting randomized latency into a zero-tolerance race-detection gate is exactly the kind of nondeterminism that design exists to avoid.

Both are ADR 0040's own already-named limitation (§"What this decision does not establish"), restated here as investigated-and-still-correct rather than left as an unexamined bullet point. Neither is pursued; both are recorded, per `docs/ROADMAP.md`'s own rule that an entry leaves the file "done, or dropped with a stated reason," never by silent deletion.

## Tests

No new test file — `allocation.concurrency.ts` (Class C) extended with round-count reporting; every other concurrency file gets the higher `ITERATIONS` value for free via the shared harness constant. `pnpm typecheck` clean; the concurrency suite confirmed to load and skip cleanly with no real Postgres target configured in this environment (`configured.concurrency.ts`'s unskippable guard fails as designed — the same signal every prior sprint touching this suite has relied on). The suite itself has not run against real PostgreSQL in this session; it runs on the existing CI gate on push, same as every other file in it.

## What this does not do

**No change to any production billing function's behavior.** `allocateReservation`'s new field is optional, defaults to nothing, and no production caller sets it. **No new infrastructure.** Supavisor and latency shaping are investigated and explicitly not adopted, for the reasons above — not silently deferred. **`CONTENTION_ATTEMPTS` is not changed.** Observability is added; the value itself is untouched pending a real measurement this environment cannot take. **No migration.**
