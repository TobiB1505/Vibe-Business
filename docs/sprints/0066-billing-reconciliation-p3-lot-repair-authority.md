# Sprint 0066 — ADR 0041 §P3: lot repair authority, proven under real PostgreSQL

Status: **Implemented. No migration, no production code change — proof and documentation only.** No new SQL function, no new column, no change to `reconcileLotAllocation`, `materialize_allocation_capacity`, or `repair_lot_allocation`.

## The gap this closes

Sprint 0065 wired `reconcileAndRepairLotAllocations` to `getBillingOverview`, reusing `reconcileLotAllocation` and `repair_lot_allocation` unchanged — the right call for wiring a trigger to an already-designed mechanism, but the mechanism's own correctness for the lot side was inherited from ADR 0041 §P3's account-side proof, never independently re-derived, and never proven under real PostgreSQL at all. Explicit instruction for this sprint: derive the lot side's source of truth from the actual code against four named candidates (Allocations, Reservations, Ledger, Allocation History), formalize repair authority, prove idempotency, and add real PostgreSQL tests — architecture first, presented and approved before any implementation.

## What the derivation found

Three parallel research passes against the actual code (not the ADR's prose about itself) established, precisely:

- **Allocations are the correct and sufficient source of truth for exactly one question** — does a lot's materialized `allocated_credit_units` agree with what its own allocation rows already say ("materialization drift")? `credit_units` is set once at insert and never rewritten; the same in-memory value feeds both the grant's CAS and the row insert, so a single call cannot self-diverge; duplicate rows are prevented by a database unique index already proven under real PostgreSQL (Race Class C); rows are append-only in every column the reconciliation reads.
- **Reservations cannot serve as an independent source, and a real gap was found**: nothing enforces `reservation.reserved_credits`/`.settled_credits` equal to the sum of that reservation's own allocations. The two agree today only because `settleOperationCredits` is the one caller of both and passes one shared value to each — and that agreement is untested and unenforced. Moot in production today specifically because every operation family settles at the full reserved amount through that one function; there is no production caller of a *partial* settlement.
- **The ledger is structurally ruled out**, not merely impractical: it has no `grant_id`/`lot_id` column in any migration, and posts one charge row per *reservation* regardless of how many lots funded it — it cannot represent a lot's current occupied capacity at all.
- **"Allocation History" is not a distinct candidate.** No separate history table exists; the current allocation rows already are the complete history. The real, structural asymmetry against the account side: the ledger separates an immutable fact from a derived cache, while an allocation row is both the fact (true from insert) and, through in-place mutation, the record of a later settlement decision — and that decision's correctness is exactly what the reservation-side gap above leaves unverified.

This produced a precise scope decision, not a vague one: `reconcileLotAllocation`/`repair_lot_allocation` are confirmed correct and unchanged for **materialization drift**. **Recording drift** — whether an allocation row's own `consumed_units` reflects what its reservation actually settled for — is named as a genuinely separate, second-order question, explicitly out of scope: folding it into `repair_lot_allocation` would repeat the exact mistake this ADR's own revision history already made once (treating "internally correct" as implying "correct relative to everything else").

**The central, previously-unproven gap**: traced directly, no concurrency test anywhere in this repository called `repair_lot_allocation`, and the one existing race touching `materialize_allocation_capacity` (`settlement.concurrency.ts`'s "partial ‖ partial") only ever raced two hot-path settlements against each other — never a repair scan against a hot-path writer, never two repair scans against each other. The row-lock authority claim §P3 rests on had real reasoning and `FakeDatabase` coverage behind it, but had never been demonstrated against real PostgreSQL specifically with a repair caller on one side of the race.

## What shipped

**A new real-PostgreSQL concurrency test**, `src/modules/credits/concurrency/lot-repair.concurrency.ts` ("Class R" — deliberately not "F," which `docs/ROADMAP.md` already uses for billing-repair *activation*, an unrelated concept). Follows the existing harness template exactly (`describe.skipIf(!configured)`, independent per-caller clients, `teardownFixture`, twenty iterations, assertions against rows read back independently, never against a call's own return value). Two scenarios:

- **Repair ‖ hot path**: four independent reservations held against one lot, released through the ordinary `releaseReservationAllocations` hot path concurrently with two `repairLotAllocation` scans of the same lot — real HTTP-level interleaving decides which side materializes which allocation first. Asserts the lot's `allocated_credit_units` always converges to zero and every allocation's `capacity_materialized_at` marker ends up set, regardless of which side won any individual row.
- **Repair ‖ repair**: allocations put into the exact state a crash between a hot-path status flip and its materialize call leaves behind (written directly, bypassing the RPC — the same fixture technique the `FakeDatabase`-level tests already use, now against real rows), then two concurrent `repairLotAllocation` scans of the same lot race with no hot-path caller involved. The literal case that was previously completely untested.

**A new `FakeDatabase`-level invariant test**, `operation-billing.test.ts`'s "keeps an allocation's settled sum equal to the reservation's own settled figure" — drives `settleReservationAllocations`/`settleReservation` (`service.ts`) directly with a partial amount (there is no production caller that does this today; every operation family settles at the full reserved amount through `settleOperationCredits`) and asserts the allocations' summed `consumedUnits` equals the reservation's own `settledCredits`. Documents the property a future variable-cost caller would depend on, as a checked test rather than an implicit assumption nothing would catch breaking.

**ADR 0041 revised in place**, sixth revision, per rule 83 — a new §P3 subsection, "Lot Repair Authority," carrying the full derivation above (all four candidates, the decision, the materialization-vs-recording-drift split, and the closed proof gap), plus a revision notice at the top matching the document's own established style. Nothing in P1, P2, P4, or the account-side steady-state design is reopened.

## What this does not do

**No production code change.** `reconcileLotAllocation`, `materialize_allocation_capacity`, `repair_lot_allocation`, and Sprint 0065's wiring are all reused exactly as they stand — this sprint is proof and documentation, not a new mechanism. **No repair for recording drift** — named as an explicit non-goal with reasoning, not solved by implication; a future sprint would need its own design if this is ever worth closing. **No migration.** **No activation** — `BILLING_REPAIR_ENABLED` stays unset, Sprint F untouched, per standing instruction. **The new concurrency test has not been run against real PostgreSQL in this session** — this environment has no local Supabase stack (`CONCURRENCY_SUPABASE_URL`/`CONCURRENCY_SERVICE_ROLE_KEY` unset); it will run on its first push through the existing CI gate (`.github/workflows/concurrency.yml`), the same as every other file in this suite.
