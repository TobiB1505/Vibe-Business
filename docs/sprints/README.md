# Sprints

This directory holds the sprint **record** for Vibe Business: one document per sprint, written after the work.

## Why

Implementation work should be scoped and recorded as discrete sprints, each tied back to [PRODUCT.md](../../PRODUCT.md) and [ARCHITECTURE.md](../../ARCHITECTURE.md), so that scope, intent, and outcome are traceable after the fact rather than only living in chat history.

## Format

A sprint document is a **record**, not a plan. It is written after the work and describes what was built, what it cost, what was decided against, and what the sprint failed to prove. It is never edited to match a later present — see [ADR 0039](../decisions/0039-documentation-currency.md).

There is no fixed template. What every document does carry:

- **What was wrong, or what was missing** — the problem in the terms it was actually found in.
- **What changed, and why that shape** — including the alternatives declined, on the evidence that declined them.
- **What was not done, and why** — deliberate omissions are part of the record.
- **What has not been proved** — the section that makes the rest trustworthy. A sprint that ran no dogfood says so; a sprint whose migration was not deployed says so.
- **Validation** — what was run (lint, typecheck, test count, build, E2E), per [CLAUDE.md](../../CLAUDE.md) rule 17.

A visual approval now binds to the `preview_sessions` row of the same commit plus the code diff — the sandbox is gone in fifteen minutes, the row is immutable and says an interactive preview of exactly these bytes ran and became reachable. **The subtle choice**: the *earliest* ready preview, not the newest, so starting a second preview to look again cannot silently move what an approval binds to (rule 68 — they did not change their mind, they scrolled the same page twice). **This sprint found a defect in the last one.** `change_approvals`' insert policy required a `ready` review artifact unconditionally, and `ra.id = null` matches no row, so the code-diff form Sprint 0113 shipped would have been refused by RLS in every customer session — passing the domain tests (in-memory, no policies), the SQL tests (inserted as the table owner, RLS not applied) and the browser tests (fixtures) alike. Rule 69's named failure mode, found only because this sprint had to rewrite the same policy; the new suite runs as `authenticated`. 411 files / 7,083 unit tests, 196 SQL/RLS against real PostgreSQL (13 new), 420 browser tests (7 new, two fixtures), lint and build clean. **Not dogfooded, and it matters more here than usual** — three assumptions about what happens inside a sandbox are reasoned and unobserved: that `next dev` starts under `deny_all` with an exposed port, that the first-request compile fits 180s, and that the public route for port 3000 exists with no prior build.
