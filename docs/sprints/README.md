## Why

Implementation work should be scoped and recorded as discrete sprints, each tied back to [PRODUCT.md](../../PRODUCT.md) and [ARCHITECTURE.md](../../ARCHITECTURE.md), so that scope, intent, and outcome are traceable after the fact rather than only living in chat history.

## Format

Each sprint document should include:

- **Goal** — what this sprint sets out to achieve.
- **Context** — why this sprint, why now, and what it builds on.
- **Scope** — what is included.
- **Non-Goals** — what is explicitly excluded from this sprint, even if related.
- **Acceptance Criteria** — how completion is judged.
- **Validation** — what was run to confirm the work (tests, build, manual checks) per [CLAUDE.md](../../CLAUDE.md) rule 17.
- **Risks / Notes** — known risks, open questions, or follow-ups surfaced during the sprint.

- [Sprint CORE-2a.1 — Audit Synthesis Contract](0023-core2a1-audit-synthesis.md) — the audit stops enumerating and starts concluding. - [Sprint CORE-2a.2 — Audit Language Boundary & Version Refresh](0024-core2a2-audit-language-refresh.md) — two residuals, both fixed at their boundary. The observed jargon leak ("no monetization model yet") turned out to be an **input** problem: the evidence pack fed the model a UI label table, then the rubric asked it not to use the words it had just been given. Founder intent is now serialized as sentences, the rubric's phrase list became one general rule, and a small output net guards six customer-facing fields only — dimension findings still say "canonical URL" on purpose. And **free entitlement is now separate from contract refresh**: an audit below the supported contract earns a `system_contract_refresh` that is free to the customer, metered internally, and never consumes or restores the entitlement — so a rubric upgrade no longer strands users on an old audit version. Dogfooded with **no manual row deletion**, which was the point. The first attempt failed on a self-inflicted defect worth recording: the third TypeScript-union/SQL-CHECK drift in this repo, caught by a helper that already existed and had not been applied — now pinned by a test. Closed with a DoD audit that itself found two gaps: both `business_audit.*` events still hardcoded the access mode (so every refresh would have been logged as the customer's included audit), and the language contract had no production-cardinality test.
- [Sprint CORE-2a.4 — Interactive Audit & "Vibe needs u"](0027-core2a4-interactive-audit.md) — **Complete.** The audit knew which facts only the founder holds and never asked. The work is the **gate**, not the questions: a lens saying "only you can answer this" produces a candidate, and between it and the founder sit founder-only, storable, material now-or-soon, prerequisite met, unasked, and within budget. Eighteen of twenty-one gate tests assert Vibe does **not** ask. One rule caught the most embarrassing possible question — a real lens reported "only you can answer what each audit run costs to deliver" while `ai_usage_events` holds that figure for every run ever made. Another caught `operating_market`, which has no canonical store and is therefore structurally unaskable rather than given a table. **A pause costs nothing**: the gate is deterministic, so it runs before the paid call. **Dogfooded on a real unrelated project — a hotel's internal vacation planner — which found two defects no test could have.** The audit's input hash includes the founder intent hash, so a run that asked a question and got an answer invalidated its own identity and died at `inputs_changed`: the answer that makes the audit better was what stopped it running. Behind that, `failOperationStep` never failed the audit row, leaving it `analyzing` inside both unique indexes — the project could no longer start any audit while the screen offered a Run button. Both fixed and covered. The completed run asked one question, produced 3 blockers with **no validation notes** at $0.1950/164s, and reasoned that a tool branded for one hotel raises a real business question — one client or many — across three lenses. A first-audit question cap was added during diagnosis and **reverted on the founder's argument**: onboarding is exactly when answers are worth most, and what made the run feel like a form was generic wording, not the count. **Next: the 9-Lens Audit Business Map UI.**

Three new browser assertions now hold it — no two cards intersect, no ring name sits under a card (typecheck/lint/3314 tests/build/151 E2E green at 1440/1280/1024/375; real dogfood still outstanding)

- [Sprint CORE-2a.3.2 — Audit Intelligence Unification](0026-core2a32-audit-intelligence-unification.md) — **Complete.** The nine-lens layer was reasoning better than the audit a founder read, and tracing the dataflow found **one cause under all three defects**: there is a single model call, and `dimensions` was the first property in the response schema. The model wrote the Monetization gaps — no pricing surface, no checkout surface, no payment integration, founder has not decided — and then wrote the customer explanation as those same four facts in the same order. It explains the priority defect too: `monetization` is a dimension scoring 10/100 written at the top of the response, while `audience` — the lens the same audit called `now` — is not a dimension at all. Judgment now goes first (`lenses → conclusions → dimensions`), each conclusion opens with an internal `rootProblem` written before any founder-facing prose exists to anchor on, and materiality became a real selection contract with overrides that must state their reason. **The same defect was live one layer downstream**: the Opportunity Engine rendered dimensions before conclusions while its own comment claimed the opposite, and the nine lenses never reached it at all. A final fix removed the rubric's own negative examples after the model reproduced a forbidden sentence near-verbatim — the third time this project primed the exact output it was banning — and traced the recurring "monetization model" leak to the **evidence id** `intent.monetization_model`, which CORE-2a.2 had left behind when it rewrote the label. **Closed on a dogfood with `validationNotes: []`, the first clean run since the lens framework existed**, and both explanations saying what their root problems say. - [Sprint CORE-2a.3 / 2a.3.1 — Business Reasoning & Stage-Aware Materiality](0025-core2a3-business-reasoning.md) — nine universal business lenses assessed before any conclusion, and then the calibration sprint the first dogfood forced. **The lenses reasoned well and ranked badly**: an audit of a `prototype` with nothing to sell put "no privacy policy" and "no analytics" in its top three, while the two problems that mattered — undecided economics, a first customer too broad to aim at — sat below the fold at `medium`. The cause was in the schema, not the model: the lens vocabulary had **no way to say "weak"**, so the model expressed severity through materiality instead. Health and priority are now separate fields (`weak` exists; materiality became temporal — now/soon/later/not_material/unknown, with `not_material` moved out of the health enum where it never belonged), rubric v6 adds the milestone and prematurity rules plus per-lens calibration and the conclusion-vs-evidence boundary, and `lens-priority.ts` records when a top three contradicts the reasoning behind it — as a note, never a rejection, after CORE-2a.3 spent $0.25 proving what discarding good reasoning costs. Dogfooded at contract v4: **five lenses now `weak`, legal and analytics correctly `later` ("expected rather than urgent right now"), and the top two are the two a founder would name** — with the entitlement still consumed and no manual row deletion. Residuals recorded: one blocker explanation still enumerates absences (caught by the new detector, not by the rubric), one sample of overfitting risk, and adaptive founder questions still wired to nothing. **Next: the Audit Business Map UI** — nine lenses with health *and* priority are computed on every run and shown nowhere.

- [Sprint CORE-2b — Action Planner Intelligence](0031-core2b-action-planner.md) — the layer between "this is the intervention I recommend" and any execution: one Move becomes an ordered path of 2–9 business actions, each naming a changed state and how anyone would know it happened. The architectural point is a split that had to be **structural rather than instructional** — the model says who has to act and what kind of change a step produces; only a server-owned capability registry says whether Vibe can execute it, and there is no wire field for a capability, an execution flag or a safety level for a model to assert one through. `vibe_executes_now` is reachable through exactly one code path and the registry has one entry, which is the honest state of the product; `vibe_prepares` exists so "this is Vibe's work" can be said without it reading as a button. Priority is never traded for automatability: the planned Move is rank 1 even when a lower-ranked one has a real executor behind it. Validation is structural rather than lexical — a completion criterion that adds no word its own title did not contain is empty, and a plan made entirely of analysis leaves the business where it started. **Then the FIX pass, before any quality was judged:** the Move → Conclusion relationship stopped being reconstructed and started being *stated* — the Opportunity Engine already knew which conclusion each Move addressed and threw it away, so `business-opportunity.v2` records it and the planner reads it, with evidence-overlap reconstruction demoted to a compatibility path that now **refuses** rather than returning a best guess when two conclusions match equally. No source conclusion means no plan and no inference, enforced by a non-nullable type rather than by call ordering, so no code path to the provider skips it. `isExecutableByVibe` made prepare-vs-execute a question code can ask, and the brittle "planner context is always smaller than an audit" invariant became assertions about what is actually excluded plus a labelled fixture expectation. Rule 57 stays enforced by walking the JSON Schema; ADR 0014 and ADR 0015 untouched; no UI (lint/typecheck/3530 tests/build/151 E2E green). **Both migrations are deployed and read back from the live database**; applying them through the management API stamped wall-clock versions instead of the filenames, so the ledger was reconciled to the files (Rule 34) and local/remote now match at 35 each. Verified by reading back rather than trusting the apply: RLS and every new CHECK present, `operation_runs` permits `action_planning`, and `business_opportunities` shows 29 existing Moves with 0 lineage — nothing backfilled, which is exactly the population the conservative legacy path exists for. **The real dogfood has not been run** — the harness is one command and writes nothing, but the five dogfood questions, the measured cost comparison and the planning timeout stay open until it does, and the first run will resolve through the legacy path because every existing Move predates `business-opportunity.v2`
