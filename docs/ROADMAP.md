## What may be in this file

This is a register of **known gaps**, not a plan and not a list of features.

- **Every entry cites something that exists** — a file path, a measured number, an ADR, or a "what has not been proved" line from a sprint record. An entry that cites nothing is a wish, and it does not belong here.
- **Entries are phrased as what is currently untrue or missing**, never as a feature to build. "Outcome verification cannot see agentic changes" is a gap. "Build an outcome dashboard" is an intention.
- **Entries leave this file two ways**: done, or dropped with a stated reason. Never by silent deletion.
- **No dates and no estimates.** The order is an argument about dependency, not a schedule.

The order below is dependency order. Correctness before foundation, foundation before breadth, breadth before fusion, fusion before the loop — because every later group consumes the earlier one.

## Now — financial correctness

*Most of this section was closed by [Sprint 0057](sprints/0057-e1-ledger-hold-correctness.md). What remains is what a local fix could not reach.* *The zero-credit settlement gap named below was closed by [Sprint 0062](sprints/0062-billing-reconciliation-e-zero-credit-settlement.md).*

**Closed — both repair triggers are wired, both authority models are derived, and activation has run against real production.**
`credits/balance.ts`/`credits/lots.ts` compute drift and both are now acted on. Sprint 0057 made an unmaterialized cache write fail loudly rather than silently, which named the shape of the input a repairer would need; it deliberately did not invent one. *Designed: [ADR 0042](decisions/0042-billing-reconciliation-authority.md)*, revised twice before implementation began. The first design (a nullable `materialized_at` on the ledger row, set "in the same call" as the aggregate) had a real crash-safety hole — the marker and the aggregate live on different tables, so setting them can never be atomic through PostgREST. Its replacement (a repair-only transactional function, called only from the account-balance read path) was itself found insufficient — proven, without needing any crash, to double-count a hot-path writer's delta if the writer's own materialization call lands after the repair commits. The shipped design shares one idempotent, per-row materialization primitive between the hot path and repair, so there is one mechanism rather than two that could disagree. **Sprint B0's schema landed** ([0058](sprints/0058-billing-reconciliation-b0-cutover.md) — the four marker columns, certified and backfilled against real Postgres), **Sprint B1's primitives landed** ([0059](sprints/0059-billing-reconciliation-b1-primitives.md) — the five idempotent functions, deployed and functionally proven against real data), **Sprint C wired the account-side hot path** ([0060](sprints/0060-billing-reconciliation-c-account-hotpath.md) — `postLedgerEntry`, `claimReservation` and `closeReservation` now call `materialize_ledger_entry`/`materialize_reservation_hold` instead of the retired compare-and-swap loops), and **Sprint D wired the lot-side hot path** ([0061](sprints/0061-billing-reconciliation-d-lot-side-hotpath.md) — `settleReservationAllocations`/`releaseReservationAllocations` call `materialize_allocation_capacity`). **Sprint C's own repair trigger (`getBillingBalance`) turned out to have zero production callers** — the real billing page calls `getBillingOverview`, which never reads the account's cached `posted_credits`/`reserved_credits` at all, so repair could never have fired even with the flag set. **Sprint 0065 closed that, and wired the lot side's repair trigger for the first time in the same pass**: both `reconcileAndRepairBalance` and `reconcileAndRepairLotAllocations` now attach to `getBillingOverview` — the one read a customer actually makes — deliberately not to `getHeaderCreditBalance` (renders on every page; its own docblock already forbids the extra query this would need) or the pre-operation admission check (latency-sensitive, and lot drift is proven one-directional and customer-negative, never a billing-safety risk). The account-side audit trail (`credit_drift.detected`/`repaired`/`repair_failed`) was itself only ever specified, never implemented, until this sprint. **Sprint 0066 then derived and proved the lot side's authority model, rather than trusting it inherited from the account side**: against four candidate sources of truth (Allocations, Reservations, Ledger, Allocation History — [ADR 0042 §P3, "Lot Repair Authority"](decisions/0042-billing-reconciliation-authority.md)), confirming `billing_credit_allocations` correct for *materialization drift* alone, naming a real, previously unenforced gap between a reservation and its own allocations' summed settlement (closed with a new test, not a repair mechanism, since no production caller settles partially today), ruling the ledger out structurally (no `grant_id` column exists, ever), and naming *recording drift* as a distinct, deliberately out-of-scope question. Its concrete finding — no concurrency test anywhere called `repair_lot_allocation`, and the one existing race near `materialize_allocation_capacity` never raced a repair scan against a hot-path writer — is now closed by [Sprint 0066](sprints/0066-billing-reconciliation-p3-lot-repair-authority.md)'s new real-PostgreSQL concurrency test, `credits/concurrency/lot-repair.concurrency.ts`. **[Sprint 0067](sprints/0067-billing-reconciliation-p3-recording-drift-authority.md) then traced recording drift itself, rather than leaving it as an open question**: `settleReservation`, `settleReservationAllocations`, and every production call site all derive from one variable — `settleOperationCredits` reads a reservation's `reservedCredits` exactly once and feeds the identical value to both the allocations and the ledger/reservation writes — so the three tables agree today by call-site accident, not by any enforced cross-check, and every traced crash-and-retry window recovers to that same single value. Two real, currently-unreachable gaps were named rather than fixed: neither settlement function compares a retry's `actualCredits` against what is already recorded, only whether one exists at all; and `refundCharge`, a real function with zero callers anywhere, would split the ledger from the allocations' `consumed_units` with nothing to reconcile them if it were ever wired up. No repair mechanism was proposed — nothing traced shows drift actually occurring — so this closes the question rather than opening new work. **[Sprint 0068](sprints/0068-billing-reconciliation-sprint-f-activation.md) then executed activation itself against real production**, following the staged procedure in [docs/deployment/billing-reconciliation-sprint-f-activation.md](deployment/billing-reconciliation-sprint-f-activation.md): merged Sprints 0058–0067 to `main` (revealing and resolving a real ADR-numbering collision with an unrelated Sprint that had independently taken "0041"), found Stage 1's migration had already been applied directly against the live database in earlier work this session, discovered Stage 2 happens automatically the moment `main` is deployed (Vercel's own GitHub integration), and — the one real finding — Stage 3's drain check failed its first run on two genuinely orphaned, five-day-stale `operation_runs` rows, cancelled only after an explicit read-only dependency sweep confirmed neither held any reservation, ledger entry, or workflow anywhere. Re-run fresh, Stage 3 passed; `BILLING_REPAIR_ENABLED=true` is live in Production, Production-only scope. The local/remote migration-version mismatch this sprint surfaced was itself reconciled the same way Sprint 0058 had already precedented once on an unrelated migration — a bookkeeping-only `UPDATE supabase_migrations.schema_migrations` per migration, never touching application data — leaving all 57 remote migration versions matching the 57 local files exactly.

**A dead `queued`/`running` operation is now swept, and a paused agent run can resume — but the resume it gets is a fresh attempt, not conversational continuation.**
`completeOperationRun` runs before `settleOperationBilling` (`business-audit/execution.ts`, and the same in action-plans and opportunities), so a sweeper keyed on a terminal operation would race settlement and produce a charge whose hold had been released. Sprint 0057 removed its planned sweeper on that evidence rather than shipping a heuristic. *Designed and implemented: [ADR 0042](decisions/0042-billing-reconciliation-authority.md) §P2, [Sprint 0063](sprints/0063-billing-reconciliation-p2-orphaned-hold-recovery.md) and [Sprint 0064](sprints/0064-billing-reconciliation-p2-agent-execution-resume.md)* — rejecting a lease/heartbeat model (a second liveness mechanism competing with Vercel Workflows, forbidden without its own ADR by rule 24) in favor of generalizing `expireStaleAgentExecution`'s already-proven "declare stale only at a read that already exists" pattern to `business_audit`/`opportunity_generation`/`action_planning`, wired into `getOperationStatus`. `needs_user` was found not to be a staleness question at all: it is now handled by an event, not a deadline — `pauseOperationForUser`'s two call sites release the hold immediately, with the reason resolved per call site (`cancelled_before_usage` for business-audit, `abandoned_with_usage` for agent-execution). Re-acquire-on-resume shipped for `business_audit` in Sprint 0063 (`runInferenceStep`, keyed per pause cycle so a replayed resume cannot double-reserve). Sprint 0064 closed the gap Sprint 0063 surfaced but could not close: `agent_execution` had no code path out of `needs_user_input` at all. `agentExecutionWorkflow`'s instance fully terminates on pause — traced against the actual Vercel Workflow code, confirmed nothing suspends it — so "resume" for agent execution means a fresh workflow instance for the same operation (`resumeAnsweredAgentExecution`, mirroring `business_audit`'s own terminate-and-restart pattern), not literal conversational continuation; the sandbox is destroyed on pause regardless, by design already in place before this gap was closed. `markAgentRunStarted`'s CAS was widened to accept a resumed run and re-stamp `started_at`, and `startAgentStep` re-acquires a reservation keyed per pause cycle, the same shape as `business_audit`'s. One real authority bug was found and fixed during that sprint's own testing, before it shipped: the existing release-on-pause code read a reservation-id snapshot taken before the resume's re-acquire, so a run that paused a second time within the same resumed invocation would have released the wrong (already-superseded) reservation. A narrower residual gap remains for `business_audit`: a crash between requeuing and re-acquiring leaves a `queued` operation with no valid hold, deliberately unswept for the same reason `queued` is never staleness-swept elsewhere — named, not fixed. Whether an agent's own context can meaningfully continue across a pause/resume cycle is untouched and stays open as a separate, larger question. The `operation_runs.pause_cycle` migration (Sprint 0063) is deployed and verified against real Postgres; Sprint 0064 added no migration — all application code reaches production through the normal PR/merge/Vercel deploy path.

**`returnToLot`'s two real callers no longer strand capacity under contention.** *Repair itself, and its trigger, are covered by the entry above.*
`lot-store.ts` used to log and give up after ten contended attempts, on the argument that returning capacity is "the customer-favourable direction" — backwards, since the customer keeps paying for Credits nothing can spend. **Sprint D wired the two callers that have an allocation row to key off** ([0061](sprints/0061-billing-reconciliation-d-lot-side-hotpath.md)): `settleReservationAllocations` and `releaseReservationAllocations` now call `materialize_allocation_capacity` instead of running their own compare-and-swap loop, so a race between two settlements (or a settlement and a release) can no longer double-return capacity or exhaust a retry budget without giving it back. `allocateReservation`'s failure-unwind path — undoing a `takeFromLot` for a plan that never committed an allocation row — deliberately keeps the old CAS `returnToLot`, for the identical structural reason `takeFromLot` itself was never converted: there is no durable row yet for the primitive to lock. This entry is otherwise closed by [Sprint 0065](sprints/0065-billing-reconciliation-p3-repair-trigger-wiring.md), covered above.

Hold safety and liveness, lost updates on both materialised columns, the allocation unique index (PostgreSQL raised `23505` and it reached the client path) and settlement interleaving each ran 20 times against PostgreSQL 17 through PostgREST, with no secret and no `pg` driver.

*[Sprint 0069](sprints/0069-postgres-constraint-gap-closure.md) then closed two of the four residuals stated above, corrected a third's premise, and investigated the fourth to a documented dead end rather than leaving it as an unexamined "still open."* **Twenty iterations missing a 5% race 36% of the time is closed**: `ITERATIONS` is now 60 (`(0.95)^60 ≈ 4.6%`), the smallest round number that gets a 5% race's miss probability under 5% — still not proof of absence for rarer races (a 1% race is still missed 54.7% of the time at sixty), which the harness's own docblock says explicitly rather than implying otherwise. **The gate's path filter is widened**: `src/modules/billing/**` and two `src/app/app/**` server-action directories reach the same tested primitives (`grantCreditLot` via the Stripe webhook, `ensureWelcomeGrant`, `getBillingOverview`'s live repair) from outside the original three directories — found by tracing every call site, not assumed, and closed via [ADR 0040](decisions/0040-ci-hosted-database-concurrency-gate.md)'s revision notice plus the widened workflow filter. **`CONTENTION_ATTEMPTS`'s stale premise is corrected, its observability gap is closed, its minimality is not**: `admitHold` no longer runs any CAS retry loop at all — ADR 0042's RPC conversion deleted it — so the constant now bounds only `takeFromLot`/`returnToLot` in `lot-store.ts`, not the function the original gap named. Those two loops now accept an optional, test-only round-count observer (`allocateReservation`'s `onContentionRound`, never passed by a production caller), and Class C reports the min/max/mean rounds a real two-way collision needed under `CONTENTION_ATTEMPTS = 10`. Actually determining whether 10 is *minimal* needs that report read from a real CI run against real Postgres, which this environment cannot execute — closing the "unobservable" half of the gap, not the "unmeasured" half, and said so rather than assumed complete. **Supavisor and network-latency parity stays open, investigated rather than left unexamined**: decompiling the pinned Supabase CLI's own service-registry code found PostgREST's backend connection is wired directly to the Postgres container in every code path, never to Supavisor, in this CLI version — enabling the pooler locally would start a fifth idle container without changing what the tested path actually traverses. Simulating network latency is technically possible on a GitHub-hosted runner but would shape the wrong hops (production's real latency is client→edge, not the internal container hops this suite's Docker network shares) and directly contradicts the suite's own zero-tolerance, no-retry design (`harness.ts`: "One safety violation... is a defect, not noise") by introducing synthetic nondeterminism into a correctness gate. Neither is pursued; both stay named, for the reasons above rather than by omission.

## Next — one shared evidence foundation

**`settleOperationCredits` and `releaseOperationCredits` are not mutually exclusive against each other, and one caller pair that could reach both concurrently already existed.**
Class D ([Sprint 0057 E2b](sprints/0057-e2b-ci-postgres-concurrency.md)) measured the primitives directly: 20 of 20 iterations of `settleOperationCredits` racing `releaseOperationCredits` on one reservation ended `released` with the charge standing and the lot's capacity consumed — deterministically, because settle does strictly more work before its close than release does. That remains true and is not itself a defect; the primitives were never meant to be the authority boundary.

What E2b's initial verification pass found, checking whether that boundary existed anywhere above the primitives for agent execution specifically, is that it did not: `finishAgentExecutionStep` (the workflow) and `expireStaleAgentExecution` (the request-time staleness backstop) both read `agent_execution_runs.status` and called into settlement or release without ever checking whether they had won anything. Both are real production callers, both are reachable — the workflow runs durably while the page polling status can independently declare the same run stale — and until the fix described below, nothing prevented the exact `charge_without_hold` state class D demonstrated at the primitive level from happening for a real customer's agent run.

The fix reuses a compare-and-swap that already existed rather than inventing an authority: `completeAgentRun` and `failAgentRun` are CAS on `agent_execution_runs.status` and both already returned whether they won — the return value was simply never checked. `execution.ts`'s `finishAgentExecutionStep` and `server-writes.ts`'s `expireStaleAgentExecution` now return immediately on losing that swap, before either reaches settlement or release, making the swap the single billing authority for one agent run — no lease, no heartbeat, no sweeper, no new table, the same pattern the three deterministic operation families already use on `operation_runs.status`. Proven against real PostgreSQL (class E, `agent-finalization.concurrency.ts`): 20 iterations with both actors racing, 20 more with the workflow winning deterministically, 20 more with the expiry winning deterministically — in every case exactly one billing terminal effect, and the `charges === 1 && reservationStatus === "released"` combination asserted impossible rather than merely counted.

Two things this fix does **not** claim. First, it does not decide whether declaring a run stale at `started_at` + the sandbox limit + a grace window is *correct* — only that whichever side wins now closes the money exactly once. Whether a run can be genuinely, safely considered stale on that basis at all is the still-open staleness-declaration question named above ("An orphaned hold is never reclaimed…") — [ADR 0042](decisions/0042-billing-reconciliation-authority.md) designs an answer (read-triggered, per-operation-type deadlines, explicitly not a lease) but does not implement it. Second, it does not make the primitives themselves mutually exclusive — class D's finding stands unchanged. Any future caller pair that can reach `settleOperationCredits` and `releaseOperationCredits` concurrently for one reservation needs its own upstream authority established the same way.

*Audited exhaustively and four more instances found and fixed by [Sprint 0070](sprints/0070-failed-start-release-authority.md).* The "nothing enforces that structurally" line above was tested rather than trusted: every production call site of both primitives was enumerated and traced back to whatever gates it. **The three deterministic families' completion and failure steps, the staleness sweep, the pause paths, and all four agent-execution finalizers are confirmed correctly gated** — the CAS boolean is checked and returned on before billing is reached, byte-identically across the six family sites. **Four were not**: the failed-start branches of `startBusinessAuditOperation`, `startOpportunityOperation`, `startActionPlanOperation` (all in `operations/service.ts`) and `startAgentExecution` (`coding-agent/service.ts`) each called `failOperationRun` and *discarded its boolean*, then released the hold unconditionally — the identical unchecked-CAS shape as the original agent-execution defect, in the identical place the E2b record warned about ("start-failure paths are where the discipline slips"). All four now gate the release on winning the swap. Reproduced red before the fix at the `FakeDatabase` level in both `operations/service.test.ts` and `coding-agent/service.test.ts` (`expected 'released' to be 'active'` — a hold released against an operation another finalizer had already completed), and proven against real PostgreSQL by a second scenario in `agent-start-failure.concurrency.ts`. **What stays open is the structural question, now stated more precisely than "nothing enforces it":** there *is* a shared wrapper (`operations/billing.ts`'s `settleOperationBilling`/`releaseOperationBilling`), but it is not an authority boundary — its guard is a status *read*, not a CAS, and its signature takes an `operationRunId` with no way to know whether the caller won anything. Making the gate un-forgettable means making the win-boolean the only way to obtain the thing that can settle or release — feasible, but it must be parameterised over *which* row is the authority (`operation_runs` for the deterministic families, `agent_execution_runs` for agent execution, deliberately) and needs a named escape hatch for the genuinely ungated-and-safe case (`coding-agent/service.ts`'s `agent_reservation_invalid` branch, where no run row exists yet). Not built in Sprint 0070; named there as its own next step rather than folded in.

A second, unrelated defect surfaced by the same verification pass: `startAgentExecution` took the Credit hold before calling `executor.start()` (money before work), but when the executor refused (`!started.ok`) nothing ever closed that hold — a deterministic leak, not a race, because the run never reaches a state the staleness backstop will touch (`queued` is deliberately ignored) and there is no reservation sweeper. Fixed by calling the same `releaseOperationBilling` the adjacent `agent_reservation_invalid` branch already used. Proven against real PostgreSQL (`agent-start-failure.concurrency.ts`): 20 iterations, each ending with the operation failed, the reservation released, no charge posted, and every lot's allocated capacity back to zero.

**A newly provisioned Vibe database now has a working Data API — but the existing tables' surplus privileges are still granted.**
None of the 54 files in `supabase/migrations/` contains a `GRANT`. The deployed project's billing tables are reachable through PostgREST only because of Postgres default privileges the Supabase platform applied — `public / tables` to `anon`, `authenticated` and `service_role`, read back from `information_schema.role_table_grants`. Supabase is moving that default to *revoke*, and `supabase/config.toml` documents the replacement behaviour: unset means new entities are not auto-exposed. So the API surface of every table is defined by a platform default rather than by this repository, against Rule 34. Sprint 0057 E2b set `auto_expose_new_tables = true` as **local/CI parity only**, and that field is removed on **2026-10-30**. Closing this means deriving PostgREST rights entirely from versioned repository configuration, under a deliberate least-privilege decision per role — `anon` currently holds `INSERT`, `UPDATE` and `DELETE` on every billing table, with RLS as the only thing refusing the write.

*Two of the three steps shipped in [Sprint 0071](sprints/0071-data-api-privilege-model.md), designed as [ADR 0043](decisions/0043-data-api-privilege-model.md).* The paragraph above is left standing as the gap's original statement; what follows corrects and narrows it. **Three of its factual claims were checked and two were wrong.** The migration count is 57, not 54 — and function-level grants have existed since Sprint B1, so "contains a `GRANT`" is false at the token level; the durable claim is that no *table-level* grant existed, which held. The exposure was **understated**: it is not "every billing table" but all 49, each carrying the full `arwdDxtm` platform default for `anon` — `TRUNCATE` and `DELETE` included. And the table count is 49, not the 50 a `CREATE TABLE` grep suggests: `project_business_context` was dropped by migration `20260816020000`, an error that would have failed the new migration on its first statement had the list not been derived from the live database instead. **What is not wrong**: RLS is enabled on all 49 tables, verified directly; every one of the 124 policies resolves `auth.uid()` — NULL for `anon` — so `anon` satisfies no policy anywhere, and the ten billing tables carry `SELECT` policies only. The system behaves correctly; what it lacks is a second line. **Shipped**: explicit per-table, per-role grants for all 49 tables (`service_role` full CRUD, `authenticated` exactly the commands its own policies exist for, `anon` nothing), and revoked default privileges so every future table must grant explicitly — which let `auto_expose_new_tables` be deleted from `config.toml` ahead of its 2026-10-30 removal. Neither changes the deployed database's effective permissions: `grant` only adds, and `alter default privileges` applies at `CREATE` time only. **Still open, deliberately**: revoking the surplus — `anon`'s writes above all. It is the only dangerous step, and it needs an empirical check that no unauthenticated path reads through PostgREST first (`anon`'s unreachability is inferred from policy predicates, not measured), plus care that revoking `SELECT` on `public.projects` would silently deny-all the 35 policies whose subqueries read it.

**Live-product evidence is now revalidated before a run that costs money — for defect ids, at the admission gate.**

Re-running the scan that produces that evidence is free and deterministic; Rule 60 forbids spending the user's money, not observing.

*Closed by [Sprint 0072](sprints/0072-live-premise-revalidation.md).* The paragraph above stands as the gap's original statement; what follows corrects it. **Its central mechanism claim was false.** `execution-contract/freshness.ts` re-checks nothing, because it never runs: `evaluateFreshness` has zero production callers (one prose mention in a comment is the only reference), and `spec.freshnessChecks` is written onto every spec and read by nothing. Adding a check there would have prevented nothing. The real gate in front of the Credit hold is `evaluateAdmission` in `execution-contract/resolver.ts`, which already performs four premise checks by hand under different names, and that is where the live check went. **The blast radius was also understated**: three of five calibration fixtures, not two runs — `sitemap_missing` and `robots_txt_missing` were false as well, not only `meta_description_missing`. **The "free" claim held**, verified by import trace: `live-product-intelligence` imports no `AIProvider` and reaches no billable provider, so Rule 60's target (re-running the Business Audit, which does synthesize with a model) is not what a re-crawl is. **Shipped**: a step's cited `live.*_missing` ids are rebuilt from a fresh-enough snapshot and refused when the defect is gone (`live_premise_no_longer_true`) or could not be observed (`live_premise_unverified`); a snapshot postdating the plan answers without spending anything, and only an older one triggers a crawl. **Deliberately narrowed to defect ids**: positive live ids like `live.surface.pricing` are out of scope, because their absence is ambiguous — renamed, behind auth, or simply not reached — and refusing a paid run on that guess is a worse failure than the one being prevented. **Still open**: `economy/execution-class.ts` derives the *pricing class* and `validation/depth.ts` the *validation depth* from the same ids at plan time, so both can still be computed from a premise that has since gone stale. The admission gate stops the run; it does not stop a wrong price being shown beforehand. *(2026-08-23, Sprint 0076: `execution-contract/freshness.ts` no longer exists — it was deleted rather than wired up. Every premise its list named is enforced somewhere that runs, and the list had never learned the live-product premise 0072 itself added, so it was a stale second description of a contract rather than a missing implementation. The sentence above is left as written; the file it names is gone.)*

**Evidence ids are minted twice, with incompatible meanings — the inverted label it caused is fixed; the id shapes themselves are not.**
`business-audit/evidence.ts` and `product-understanding/evidence.ts` each build ids from the same snapshots. `repo.surface.<id>` means "present" in one and "present or absent" in the other, distinguished only by the label — while `evidence-v2.ts` argues in its own comments that polarity must live in the id.

*Partly closed by [Sprint 0073](sprints/0073-evidence-id-polarity.md).* Every claim above is confirmed, and the entry **understated it**: this was not latent id hygiene but a live, founder-facing defect. `describeEvidenceId("repo.surface.payments")` rendered **"Payments, in your code"** — marked `curated`, so not even visibly a fallback — against a pack whose own label read *"Repository surface not detected: Payments"*. The meaning was inverted on screen, in the "Why?" disclosure, for every one of the 14 business surfaces and every live surface. Verified by executing the real builder against a real fixture, not by reading. Two further findings: `evidence-labels.ts`'s comment claimed `_not_observed` was "the authenticated **and repository** vocabulary" — false, no minter has ever emitted `repo.surface.*_not_observed`; and the test guarding all of this derived its id list from the same label tables it asserted against, so it was structurally incapable of catching an id a builder mints and the table lacks. **Shipped**: polarity-free surface ids now name the check rather than its outcome ("Payments, checked in your code"), `_missing` and `.not_found` joined the absence-suffix set, and the guard now harvests ids from the real builders. **Still open, and deliberately not attempted**: the id shapes themselves. **The evidence pack is the load-bearing artifact of the whole reasoning chain and is never persisted.**
Audit, opportunities and planner each rebuild it from *current* snapshots. Citations inside a stored audit are references into a document that no longer exists; only the input-hash gates keep them resolvable.

*Corrected and closed by [Sprint 0074](sprints/0074-evidence-pack-provenance.md).* The paragraph above stands as the gap's original statement; what follows corrects it. **The harm it names does not occur.** `describeEvidenceId` resolves from the id alone, deliberately, so that a stored citation stays readable long after its pack is gone — Sprint 0073 pinned that as a property. A citation whose pack no longer exists renders exactly as well as one whose pack does; resolvability was never the exposure, and no screen depends on the pack being retrievable. **The harm that does occur burns money.** What the input-hash gates were assumed to keep is the premise that a rebuild reproduces the audit's pack — and on two of the three consumers they did not. `computeOpportunityInputHash` contains the audit's id, the audit's own stored `input_hash` and seven version constants; `computeActionPlanInputHash` adds the Move, the conclusion key, the profile and the founder intent. **Neither contains a snapshot id**, and the audit row is not rewritten when a scan finishes — so a repository or live scan completing between the click and the durable step moved what `getLatestSuccessfulSnapshot` returns without moving one field either hash covers. Nothing crashed: the audit's citations are ids a builder still mints, so they still rendered, pointing at a different observation than the sentence above them. A paid call prioritized one run's diagnosis using another run's evidence, invisibly. **Shipped**: `business-audit/pack-provenance.ts`, checked against the audit row rather than against click time (*"are these the inputs the audit reasoned from?"*, not *"the ones the user clicked on?"*), returning the existing `inputs_changed`; and `business-audit/store.ts` now reads back `repository_snapshot_id`/`live_snapshot_id` — `not null` and written on every row since the table existed, never once selected. A null profile or intent hash is skipped (genuinely nullable pre-CORE-2); a null snapshot id **refuses**, because it cannot come from production and a guard that passes on absent data passes vacuously. **A second finding**: `operations/action-plans/execution.ts` had no test of any kind — wired straight into the Vercel executor, never exercised below the workflow — so the guard could only go red on one of its two call sites until this sprint wrote the planner's first one. **Still open**: the Deep Scan snapshot is not compared. `computeAuditInputHash` hashes `authenticatedSnapshotId` from a live lookup and nothing writes it to a column, so there is nothing on the audit row to compare a rebuild against; a Deep Scan finishing mid-operation still moves the pack unseen. Closing it needs a column and a migration. **Not attempted, and deliberately**: persisting the pack. That would put repository- and website-derived content into a durable store (Rules 26, 37) and into the execution provider's log (Rule 52). Rebuilding is the right design; the check that the rebuild reproduces what it claims to is what was missing.

## Then — measurement truth, then breadth

**The calibration dataset is too thin to calibrate anything.**
*Narrowed by Sprint 0055 (2026-08-22): validation CPU is no longer the blocker — the fix is verified, and runs 3, 4 and 5 recorded non-null `active_cpu_ms` every time.* What remains is the sample: three comparable runs at a mean absolute error of **53.4%**, roughly double the backtest's 24.3%, against a cohort sample floor of 20 below which the correction is exactly 1. Runs 1 and 2 stay `actual_incomplete` and contribute nothing. More runs is the only thing that closes this; a cleverer formula is not.

**Cache token quantities are not metered, though their cost now is.**
*Narrowed by Sprint 0057 E2 (2026-08-22): the cost half is closed. `costForAiRow` prices cache reads and writes, which repaired 234 of the live ledger's 314 AI rows — every row carrying cache tokens was reported by `reconcileAiUsage` as a §69 cost mismatch, because the ledger priced cache and the projection did not.* What remains is the metering half: there is still no `anthropic_cache_read_tokens` or `anthropic_cache_write_tokens` SKU, and adding one is a migration because `billing_usage_events.sku` carries a CHECK constraint listing every value. It becomes chargeable-behaviour rather than reporting detail the moment a Credit rate card exists, since `rating.ts` rates per SKU quantity — `ECONOMY_MODEL.md` measured cache at 55–70% of agent provider cost, and a card would charge for none of it. `CREDIT_RATE_CARDS` is empty, so nothing is mischarged today.

**Sandbox rates are founder-attested and unverified.**
`economy/infrastructure-rates.ts` carries `sourceKind: "founder_attested"` on every rate. One reconciled invoice would move the whole sandbox cost layer from attested to verified.

**Repository intelligence cannot see what execution needs.**
`package.json` scripts are parsed and discarded, then re-parsed inside the sandbox in two places; there is no test-infrastructure, CI, e-mail or feature-flag detection; and `runtime` is empty for anything that is not Node or Docker.

**Live product intelligence is homepage-centric.**
All eight document-level SEO signals and the entire brand block are read from the homepage only. `/pricing` is fetched at top priority and yields a title and CTA labels — no prices, plans or billing period — for a product whose central dimension is monetization. Headings are parsed, capped at 40 per page, and thrown away.

**A client-rendered product produces an almost empty scan with no warning.**
There is no rendering signal, so "we could not read this" is indistinguishable from "there is nothing here" — the failure mode the audit's own `insufficient_evidence` rule exists to prevent.

## Later — the loop, and what it is blocked on

**Outcome verification cannot see agentic changes.**
`execution/outcome-contract.ts` maps `agentic_execution_v1` to `null`, so every change the coding agent produces resolves to `outcome_not_supported`. The measurement half of the product is wired to two deterministic SEO generators.

**Business outcome measurement has no data source.**
Three metrics are defined and the port is vendor-neutral, but no adapter exists; every project resolves to `waiting_for_source`. Draft PR #34 holds partial Search Console work from 15.08.

**Snapshot history is complete, immutable, and never read.**
All four snapshot tables retain every version; no code compares two. A re-scan that loses the pricing page produces a new audit with no note that anything disappeared.

**Nothing learns from a run.**
`agent_execution_runs` carries around ninety observation columns and `execution-context/verification.ts` names the feedback in prose — a validation failure on a run whose agent verification was `low` "is exactly the signal that would justify moving a task class up a mode" — and nothing reads it. `economy/intelligence/` is the one correctly-built learning layer and is deliberately unwired.

**The unit that is charged and the unit that is sold are different things.**
An agent run settles at the reserved fixed price when the prepared change exists; validation runs afterwards, unreserved and uncapped. A validation failure after a successful preparation still charges.

**No operator can correct a charge.**
`refundCharge` is implemented, tested through its decision function, constrained by a database CHECK — and has zero callers. So does the adjustment kind. There is no admin surface of any kind.
