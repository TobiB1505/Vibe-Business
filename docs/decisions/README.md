# Architecture Decision Records (ADRs)

This directory holds Architecture Decision Records: short documents that capture a significant architecture or product-behavior decision, the context that led to it, and its consequences, at the time it was made.

## Why

[ARCHITECTURE.md](../../ARCHITECTURE.md) intentionally lists a number of open decisions rather than pretending they are already settled. As each of those (or other significant decisions) is actually made, it should be recorded here — not only discussed in chat — so the reasoning survives independently of any single conversation. See [CLAUDE.md](../../CLAUDE.md) rule 13.

## When to write an ADR

Write one when a decision:

- Is hard or costly to reverse, or
- Affects multiple layers/modules described in [ARCHITECTURE.md](../../ARCHITECTURE.md), or
- Resolves one of the open decisions explicitly listed in ARCHITECTURE.md, or
- Meaningfully changes product behavior described in [PRODUCT.md](../../PRODUCT.md).

Small, easily reversible implementation choices do not need an ADR.

## Naming

Sequential, numbered, kebab-case, descriptive:

```
0001-github-as-integration-layer.md
0002-preview-deployment-strategy.md
```

- [0068](0068-retention-periods.md) — Retention periods, by what the data is for (Accepted. Closes [ADR 0056](0056-lifecycle-erasure-and-retention.md)'s deferred P-2, which forbade inventing a duration in an implementation. **First it separates two problems PERF-018 put in one finding**: `max_rows = 1000` truncating an unbounded read is a *correctness* defect — a well-formed wrong answer to a sum — and deleting old rows only moves the date it starts being wrong, so completeness reads must aggregate or paginate whatever the period is. Retention answers cost and privacy, and nothing else. **Four classes, because there are four regulators**: financial records ten years (HGB §257 / AO §147 statutory minimum, which GDPR Art. 17(3)(b) does not shorten — which is why erasure tombstones this graph); the audit trail eighteen months, so an incident noticed late still has a full prior year behind it; operational event streams ninety days, the highest write rate and the lowest retained value; and derived intelligence by **count, not age** — the latest three per project, because an age rule would delete a quiet project's only audit and leave a founder reading "not analysed yet" for work they paid for. `ai_usage_events` deliberately follows the financial class rather than the operational one, because ADR 0056 §7 already established that deleting metering while keeping the charge makes "why was this account charged" unanswerable. **The sweep for the financial class is not a row-age sweep**: ADR 0056 F5 proved partial deletion has no repair path, so it may act only on an already-tombstoned account and only on the whole graph at once. Periods are named constants in code — not environment variables, not a dashboard — because a period changeable without a diff makes ADR 0056 §6's own rule unenforceable. **Left open on purpose**: whether a Credit ledger row is a `Buchungsbeleg` is a tax advisor's determination, so ten years is adopted as the safe direction — keeping a commercial letter too long is lawful, destroying a booking voucher early is not)
- [0069](0069-retention-sweep-trigger.md) — What deletes the expired rows, and what it may not touch (Accepted. Closes [ADR 0068](0068-retention-periods.md)'s deferred D-2, which decided four retention periods and deliberately no mechanism — so nothing deleted anything and the policy was a document. **The option 0068 nominated first was evaluated and fails**: read-triggered sweeping reaches only rows somebody reads, and nobody reads a ninety-day-old event, while any activity-amortised variant never fires for an account that has stopped being active — the exact case Art. 5(1)(e) is about. Retention needs a clock. **`pg_cron` over Vercel Cron**, because deleting rows is a database operation and the alternative's cost is an authenticated internet-reachable endpoint whose only job is to destroy data; it also keeps running while the app is paused or mid-deploy. The job is scheduled by `cron.schedule` **inside a migration**, so the repository states the schedule and a job unscheduled in the dashboard is a detectable divergence rather than a silent one; the function is `security invoker` with `execute` revoked from every Data API role, so cron is its only caller. The periods stay in TypeScript and the SQL is a second copy pinned by a test that reads both files as text — the instrument Sprint 0118 built for the poll interval. **Writing it found three things that made ADR 0068 §5 unsafe as worded**: `operation_runs` is the parent of six cascade edges, so an age sweep of it would delete the `prepared_changes`, `review_artifacts` and `validation_runs` a human approval binds to under rule 67 — out of scope at any period; `sandbox_usage_events` and `review_browser_usage` are billing sources that reconciliation projects into `billing_usage_events`, so they follow the financial class rather than the ninety-day one; and `agent_execution_events` is the only record behind rule 78's measured agent cost, which does not change its period but obliges the economy module to state its rolling horizon so an analysis cannot read a truncated window in silence. Two classes are enforced, two are not — the financial sweep cannot delete anything before 2036 and is not written, the count-based derived rule needs a different instrument — so the privacy-page disclosure lands per class as each becomes true, because a published period nothing honours is a false statement rather than a gap)
