# 0041 - Billing Reconciliation Authority

Status: Proposed
Date: 2026-08-22
Builds on [0013](0013-durable-operation-execution.md) (durable execution, and rule 24's origin), [0024](0024-vibe-credits-economic-layer.md) (the economic layer this governs)

> **Revision, 2026-08-22, before implementation began.** The P3 mechanism as first written below (`materialized_at`/`capacity_settled_at` markers, set "in the same call" as the aggregate write) contained a real correctness error: the marker and the aggregate live on different tables, so they cannot be set by one PostgREST statement, and the claim that they could was wrong when written, not merely superseded. Re-examination — prompted by an explicit request to prove crash safety, not only concurrent-writer safety, before Sprints B–D began — found the marker design cannot satisfy I5 at all. §P3 below is the corrected mechanism (an atomic, narrowly-scoped repair function, not a marker). §P2 is also revised: `needs_user`/`needs_user_input` are removed from the staleness model entirely, in favor of releasing the hold on entering the wait and re-reserving on resume, which was found to be the actually-correct fix rather than a harder scheduling problem. The original, incorrect P3 text is kept below the corrected version, marked, rather than deleted — see "What P3 originally said, and why it was wrong."

> **Second revision, 2026-08-22, before Sprint B began.** Three proof obligations were raised against the revision above: (1) prove `repair_account_balance`/`repair_lot_allocation` share the same serialization authority as every hot-path writer, so a writer whose ledger/allocation row committed before a repair ran can never re-apply its own delta after the repair commits; (2) correct the "no migration required" claim, and specify a security model for the functions; (3) determine whether provider usage can already be economically outstanding before `needs_user`/`needs_user_input`, and if so what the financially correct release semantics are. All three are answered below. The first is the significant one: **the prior revision's P3 design does not satisfy Obligation 1 as written, proven directly against `applyPostedDelta`'s real code, with no crash required** — ordinary concurrent timing is sufficient. The corrected mechanism no longer claims the hot path is unchanged: four of five hot-path CAS writers (`applyPostedDelta`, `admitHold`, `releaseHeldCredits`, `returnToLot`) move to a function-based primitive shared with repair; one (`takeFromLot`) stays untouched, for a structural reason the proof also establishes. §P3 is rewritten below; the prior revision's text is preserved, marked, per rule 83, alongside the original marker design it had already superseded. §P2 gains the pre-pause usage analysis Obligation 3 asked for — its conclusion (release-on-pause, re-reserve-on-resume) is unchanged, and this revision adds which release reason applies at which pause site, and why.

> **Third revision, 2026-08-22, before Sprint B began.** The steady-state mechanism from the second revision (hot path and repair sharing the transactional `materialize_*` primitives) is accepted and unchanged by this revision. What was missing is how the system safely *reaches* that steady state from today's schema and today's already-running code — a fourth proof obligation, answered in a new §P3 subsection, "Rollout." It establishes, with evidence rather than an assumption: existing rows cannot be replayed merely because the marker columns are new (R1); an old-code writer mid-deploy cannot create a row a newly-activated repair misreads as pending (R2); and there is one precise, operator-verified point before which repair cannot act on a `NULL` marker as evidence of anything (R3). Nothing in P1, P2 or P4 changes.

> **Fourth revision, 2026-08-22, before Sprint B began.** Two details inside the accepted Rollout mechanism were underspecified, not wrong: (1) R1's "certifies, in SQL, inside its own transaction" did not itself close the READ COMMITTED race between the certification's reads and a concurrent writer's commit — closed below with explicit table locks, in a fixed order, derived from each writer's actual statement type, with `NOWAIT` so an unobtainable lock fails the migration rather than hanging it. (2) R3's "drain window... verified operationally" named the right idea without naming the exact, mechanical, observable condition — named below as an exhaustive enumeration of every writer source this codebase's own architecture permits (rule 24 bounds the enumeration to two categories: ordinary invocations and Vercel Workflow instances — nothing else is allowed to exist), with the workflow condition defined to explicitly cover a run parked in `needs_user`/`needs_user_input` at cutover time, which is financially resolved by P2 but not execution-drained. P1, P2, P3's steady-state design and P4 are unchanged; nothing here reopens them.

## Context

### What Sprint 0057 already established, and where it stopped

Sprint 0057's corrective work (documented in [the E2b sprint record](../sprints/0057-e2b-ci-postgres-concurrency.md)'s "Verification found two real defects" section) proved a principle this ADR now names and generalizes: **a compare-and-swap on an entity's own terminal-status column is the only authority permitted to finalize the money tied to it.** Two independent implementations already carry it:

- Every deterministic operation family (`business-audit`, `opportunities`, `action-plans`, and the rest) gates its billing calls on `completeOperationRun`/`failOperationRun`'s return value — both are CAS on `operation_runs.status`, both return whether *this call* won the swap, and every caller has always checked it before reaching `settleOperationBilling`/`releaseOperationBilling`. `business-audit/execution.ts:656-682` is the canonical instance: `const transitioned = await completeOperationRun(...); if (!transitioned) return;` — the comment above the charge is explicit: "the charge inherits exactly-once from the state machine rather than needing its own guard."
- Agent execution's two independent finalizers — `finishAgentExecutionStep` (the durable workflow) and `expireStaleAgentExecution` (a request-time backstop) — did **not** check the equivalent boolean until Sprint 0057's corrective commits (`78b1888`, `2d99764`). Before that, both could finalize the same reservation; E2b measured the resulting `charge_without_hold` state 20 times out of 20 under real PostgreSQL MVCC. The fix reused `completeAgentRun`/`failAgentRun` — CAS on `agent_execution_runs.status`, already returning the boolean, simply never checked — rather than inventing anything.

So the *authority* half of the problem — who may act — has one answer, proven twice. What Sprint 0057 deliberately did not solve, and named as out of scope both times, is the four gaps `docs/ROADMAP.md` still lists under "Now — financial correctness":

1. **Drift repair.** `balance.ts`'s `reconcileBalance` and `store.ts`'s `MaterializationError` detect that a materialized cache column has stopped agreeing with the ledger that defines it. Nothing repairs it. `store.ts`'s own comment on `MaterializationError` says so: *"There is no repairer in this codebase — `reconcileBalance` computes drift and nothing acts on it — so the only honest response is to fail loudly."*
2. **Orphaned holds.** `operations/store.ts`'s terminal transitions are reachable only by a live step calling them. A workflow that dies mid-run — the exact failure `expireStaleAgentExecution` was built to answer for agent execution — has no equivalent backstop for any deterministic operation family. `completeOperationRun`/`failOperationRun` are gated on `ACTIVE_STATUSES = ["queued", "running"]` (`store.ts:86`); nothing ever calls them for a run nobody is watching.
3. **Stranded lot capacity.** `lot-store.ts:284`'s `returnToLot` logs and gives up after `CONTENTION_ATTEMPTS` (10) contended writes, on the stated argument that giving capacity back is "the customer-favourable direction" — which is backwards: the customer keeps paying for Credits nothing can spend.
4. **Zero-credit settlement is not idempotent.** `service.ts`'s `settleReservation` finds a retry's existing charge by ledger idempotency key — but `billing_credit_ledger.credit_delta <> 0` is a CHECK constraint (`20260817180000_billing_credits_core.sql:98`), so a zero-credit settlement posts no ledger row at all. A retry finds nothing, falls into `decideSettlement`, sees `reservation.status !== "active"` (already closed by the first attempt), and refuses with `reservation_not_active` — reporting a real success as a failure.

The user's instruction for this document is explicit: analyze these four as one architecture, not four bugfixes, and design the ADR — implementation is separate, later work.

### The precedent that already answers "how, without new infrastructure"

`expireStaleAgentExecution` (`operations/agent-execution/server-writes.ts:279`) already solved "nothing ever comes back to close an abandoned run" for exactly one case, and its own docblock states the doctrine this ADR generalizes:

> "The polling loop terminates every run it is watching. What it cannot do is survive the workflow itself dying... A durable execution that can leave a customer's Credits reserved forever is not one, so there has to be an answer that does not depend on the workflow being alive to give it. This is that answer: a read path notices, and repairs... Because the read is the moment it matters. Somebody is looking at this run's status; the alternative is a cron this product does not have and would need a decision to introduce (rule 24)."

It is fired from `getAgentExecutionStatus`, which the run page already polls. No sweeper, no schedule, no new table — a read chokepoint that already existed, carrying one more check. This is the shape every mechanism below reuses.

### Two detectors already exist and are already unused

`balance.ts`'s `reconcileBalance` and `lots.ts`'s `reconcileLotAllocation` are both pure functions that already compute "what should this cache column read, given the durable rows that define it" — for the account (`posted_credits`/`reserved_credits` vs. the ledger) and for a lot (`allocated_credit_units` vs. its allocation rows), respectively. Both have exactly the callers I1-I3 left them with in Sprint 0057 E1: `reconcileBalance` is called once, by `getBillingBalance`, which logs and returns the drifted figure anyway; `reconcileLotAllocation` has no caller at all. Neither needs to be invented. What is missing is the repair half, and the trigger.

### A gap this analysis found that neither Sprint 0057 nor the ROADMAP names

`operation_runs`'s terminal CAS (`completeOperationRun`/`failOperationRun`) is gated on `ACTIVE_STATUSES = ["queued", "running"]` — it does **not** include `needs_user`, even though `schema.ts`'s `isActive()` counts `needs_user` as active, and its own comment says why: *"A run waiting for an answer still holds..."* its reservation (`schema.ts:248`). An operation paused on a founder's answer that never comes is therefore invisible to the terminal CAS today — there is no path that ever fails it, staleness-aware or not.

Agent execution's own terminal CAS (`failAgentRun`/`completeAgentRun`, `coding-agent/store.ts:680-717`) already includes `needs_user_input` in its gate — so this specific asymmetry is `operation_runs`-only, not systemic. But `expireStaleAgentExecution`'s own eligibility check (`run.status !== "running"`, `server-writes.ts:305`) excludes `needs_user_input` from staleness *declaration* regardless — so a paused-forever agent run is unreachable for a different reason: nothing ever asks whether it should be declared stale. Both families therefore share the same live gap at the staleness-declaration layer, for a structurally different reason at the authority layer. Any design that only widens `expireStaleAgentExecution`'s pattern without addressing this is incomplete, and is treated as such below.

## Decision

Every one of the four gaps is one of exactly two questions — **who may act**, and **what is the durably correct value** — and both questions already have one answer apiece, proven or half-built. This ADR is four applications of two mechanisms, not four designs.

### P1 — Terminal-transition CAS is the only billing authority (doctrine, now named rather than emergent)

Restated as a standing rule rather than a pattern that happens to appear twice: **any entity that can independently trigger settlement or release of Credits must expose a CAS on its own terminal-status column, and every caller of a billing-affecting transition must check the boolean it returns before touching money.** `operation_runs.status` and `agent_execution_runs.status` are the two existing instances; a future billable entity (a third finalizer, a new execution surface) inherits this by doctrine, not by copying code.

**P1 needs no correction.** The needs-`needs_user`-widening this section originally required is withdrawn — see the revised P2 below, which removes the reason for it.

### P2 — Staleness is declared only at a read that already exists, never on a schedule; `needs_user` is not staleness at all

**Revised.** The first version of this section tried to fold `needs_user`/`needs_user_input` into the same staleness-deadline model as a dead workflow, and required widening `operation_runs.ACTIVE_STATUSES` and `agent_execution_runs`'s eligibility to reach it. Re-examined: that both requires guessing a policy that is genuinely hard to calibrate (how long is too long to wait for a founder to answer a question — too short interrupts a real answer, too long defeats the point) and treats the wrong symptom. The actual question is not "when has a human waited too long" — it is "why is money held reserved at all while nothing is running."

**It should not be.** A reservation exists under §18/§55's "money before work" principle to guarantee capacity for work about to happen. While an operation sits in `needs_user`/`needs_user_input`, no provider call is in flight, nothing is being spent, and nothing is at risk of being raced away by another operation — the premise that justified taking the hold does not hold during the wait. `pauseOperationForUser` (`operations/store.ts:335`) and its agent-execution equivalent, checked directly: **neither releases the reservation today.** `business-audit/execution.ts:450` and `agent-execution/execution.ts:1118-1119` both call `pauseAuditForQuestion`/`pauseAgentRunForUser` and `pauseOperationForUser` with no billing call anywhere near either site — this is a real, previously unnamed gap, not a hypothetical.

**The fix:** release the hold at the same moment the operation enters the wait state, and re-authorize (fresh `authorizeOperationCredits`/`holdAgentExecutionCredits` call, re-pricing from whatever policy is current, exactly as a brand-new operation would) at the moment it resumes (`requeueAnsweredOperation`). This is not a new mechanism — it is the *existing* release/reserve primitives, called at two points that do not call them today. It eliminates the orphaned-hold question for this state entirely rather than answering it: an operation abandoned in `needs_user` forever now holds **nothing**, so there is nothing to reclaim, no deadline to calibrate, and no staleness declaration ever needed for this state. `ACTIVE_STATUSES`/`agent_execution_runs`'s eligibility do not need widening, because by the time either state is reached, its billing is already fully resolved.

**The cost, named rather than hidden:** re-authorization on resume can fail — the customer may have spent the reserved balance elsewhere while waiting. This is a real, new failure mode the original design (hold forever) did not have, and needs its own product-level answer (most likely: fail the operation with a distinct, clear failure code — "insufficient credits to resume" — rather than the generic staleness code this ADR otherwise uses). That is a small, well-scoped decision for the sprint that implements this, not a design gap this document leaves open.

**Pre-pause economic exposure, checked per call site, not assumed (Obligation 3).** Releasing a hold on entering `needs_user`/`needs_user_input` is only complete once it is also asked what the release is releasing — whether real, unrecoverable provider cost was already incurred against the reservation before the pause, and if so, whether the release should say so. Checked directly against both call sites, not inferred:

- **`business-audit/execution.ts:450`.** `pauseAuditForQuestion`/`pauseOperationForUser` fire at `stage: "asking_founder"` (line 448), strictly before `stage: "counting_tokens"` (line 486) and `stage: "running_ai"` (line 557) — no AI inference, and therefore no provider spend, has occurred by the time this pause is reached. Released with `releaseOperationBilling(..., providerUsageOccurred: false)` → `cancelled_before_usage`, matching what actually happened: nothing was spent.
- **`agent-execution/execution.ts:1118-1119`.** `pauseAgentRunForUser`/`pauseOperationForUser` fire *after* a completed harness invocation whose tool-call and activity counters (`gateway.counters`, `recordAgentToolEvents`, `recordAgentActivity`, lines 1098-1107) are already being read and recorded — real tool calls, and the provider spend they represent, have already occurred by the time this pause point is reached. This is a genuine instance of the exposure the obligation describes: reserve 100, real usage accrues, then `needs_user_input`. Released with `releaseOperationBilling(..., providerUsageOccurred: true)` → `abandoned_with_usage` — the reason already built for exactly this shape (`balance.ts`'s own docblock: "An operation can fail after spending real provider money... `abandoned_with_usage` ... keeps the usage attached so the decision can be made later"), which flags `usageOutstanding: true` rather than silently discarding the fact that real cost was incurred.
- **No other operation family pauses.** `opportunities` and `action-plans` never call `pauseOperationForUser` or an equivalent — grepped directly across `src/modules/operations/`, confirmed absent. The two call sites above are exhaustive for this ADR's scope.

**What this deliberately does not do.** It does not settle the consumed portion and release only the remainder (the user's option (a)) — `decideSettlement`'s own documentation states fixed-price operations have no partial-charge path today, and building one is a new billing primitive outside this ADR's scope. It does not silently discard the pre-pause cost either — a bare release with no flag would be indistinguishable from "nothing happened," which `abandoned_with_usage` exists specifically to prevent. What it does is record, honestly, using a mechanism this codebase already approved and already ships (`RELEASE_REASONS`, `decideRelease`'s `usageOutstanding`), that real cost was incurred at the one call site where it can be, and that the commercial question of who bears it is still open — the codebase's existing answer to "provider cost happened, no charge exists yet," applied at a pause site rather than invented for one. This does not change the release/re-reserve conclusion above; the two questions (should the hold be held across the wait; was anything already spent before the wait began) turned out to be independent, and the answer to the second is now explicit rather than assumed.

**What P2 keeps from the original design, unchanged:** for `queued`/`running` — a workflow that is genuinely dead, not paused — the read-triggered generalization of `expireStaleAgentExecution` stands as originally proposed: a shared `expireStaleOperation`, wired into `getOperationStatus` the way `expireStaleAgentExecution` is wired into `getAgentExecutionStatus`, governed by a per-operation-type deadline table (never one constant, for the reason `AGENT_SANDBOX_LIFETIME_MS` is specific to agent execution's own sandbox bound), calling the existing terminal CAS and reporting nothing expired on a lost swap. Explicitly out of scope, restated: whether an operation abandoned in `needs_user` forever should eventually be cleaned up for non-financial reasons (stale UI state, operator hygiene) is a real question and is not this ADR's — nothing is financially at stake once the hold is released, and "Now — financial correctness" is the only thing this document governs.

### P3 — Repair and hot-path materialization share one idempotent primitive; a repair-only function was not enough

**Revised again. The repair-only function below (kept, marked, as the record of what the first revision proposed) does not satisfy the invariant it was asked to prove, and the error was found before any migration was written, which is exactly why this document asked to stop there a second time.**

**The failure, proven against the actual code, not against the design's own description of itself.** `postLedgerEntry` (`store.ts:253`) inserts the ledger row as its own committed statement, then calls `applyPostedDelta` (`store.ts:408`) as a *separate*, later call to materialize the delta into `posted_credits`. Nothing makes those two calls atomic with each other — that gap is exactly what the prior revision's repair function was supposed to be safe against. It is not. Trace a concurrent repair through it:

1. Writer B's ledger row for `delta_B` commits (`postLedgerEntry`'s insert). B has not yet called `applyPostedDelta`.
2. `repair_account_balance`, as the prior revision specified it, starts: `SELECT ... FOR UPDATE` locks the account row, recomputes the total by summing **every** ledger row for the account — which already includes B's just-committed row, because a committed row is durably visible to any reader. The recomputed total therefore already reflects `delta_B`. Repair writes it and commits, releasing the lock.
3. B's `applyPostedDelta` now runs its first attempt — not a lost race, B's very first read: `SELECT posted_credits` reads the repair-corrected value, which already includes `delta_B`. B computes `next = read_value + delta_B` and writes it, guarded by `.eq("posted_credits", read_value)`. Nothing has touched the row since repair committed, so the CAS **succeeds**.
4. `posted_credits` now equals `(V_old + delta_B) + delta_B` — `delta_B` applied twice. I5 fails, and no crash appears anywhere in the trace.

The prior revision's own text claimed the opposite: that an ordinary CAS writer "queue[s] behind the lock and proceed[s] normally once it releases, reading whatever the function just corrected and adding their own delta on top **exactly as they already do when racing an ordinary writer**." That comparison is the error. Racing an ordinary writer is safe because neither writer's delta is already reflected in what the other reads. Racing this repair is not the same case: the repair's recompute is *defined* to already include every committed ledger row, including one whose CAS materialization has not run yet — so the writer reads a value that already contains its own not-yet-applied contribution and has no way to know that, because nothing distinguishes "this value already reflects a foreign repair that folded in my delta" from "this value reflects everyone else's deltas but not mine," which is the only case the CAS retry logic is built to handle. A `SELECT ... FOR UPDATE` row lock serializes *access* to the row for its own duration; it says nothing about whether a reader arriving strictly after the lock releases can correctly interpret the value it finds there. That is exactly the property this design needed and did not have.

The identical failure applies to `repair_lot_allocation` against `returnToLot` (`lot-store.ts:248`), for the same structural reason: `settleReservationAllocations`/`releaseReservationAllocations` flip an allocation's `status` to `consumed`/`released` as one committed statement, then separately call `returnToLot` to materialize the capacity return. A repair recomputing `allocated_credit_units` from the current allocation rows, running between the status flip and `returnToLot`'s own call, already counts the return; `returnToLot`'s subsequent CAS attempt reads the repair-corrected value and subtracts the same amount again — understating `allocated_credit_units`, the mirror-image error (phantom capacity instead of a phantom charge), same cause.

**What does not fail this way, and why the distinction matters.** `takeFromLot` (`lot-store.ts:198`) has no such gap. It materializes `allocated_credit_units` *before* the allocation row that records the take is ever inserted — `allocateReservation` (`lot-store.ts:299-354`) calls `takeFromLot` for each planned allocation and only inserts the allocation rows afterward, once every take has succeeded. There is no durable row a repair could read to learn about a take that has not yet materialized, because the take *is* the materialization; nothing describes it independently and earlier. `reconcileLotAllocation`'s drift is therefore one-directional in practice — `allocated_credit_units` too *high*, from an unreturned capacity return, exactly what the ROADMAP names as gap #3 — never too low from a missed take, and `takeFromLot` needs no change. This is why the fix below touches four hot-path writers, not five.

**`admitHold` has the identical gap, for a reason this document had not yet named.** `claimReservation` (`store.ts:576`) inserts the `billing_credit_reservations` row first, as its own committed statement, then calls `admitHold` (`store.ts:664`) separately to materialize `+reserved_credits` — row-then-materialize, the same order as the ledger, not the lot-take order. `reconcileBalance` recomputes `reserved` from active reservations the same way it recomputes `posted` from ledger entries, so a repair running between a reservation's insert and its `admitHold` call already counts it, and `admitHold`'s subsequent first attempt double-counts it on top — the same trace as steps 1–4 above, with "reservation admitted" in place of "ledger entry posted." `MaterializationError`'s own `column: "posted_credits" | "reserved_credits"` type already named both as capable of the same drift; this proof is the reason both need the same fix, not an extension added for symmetry's own sake.

**The corrected mechanism: one idempotent, transactional primitive per cache, called identically by the hot path and by repair.** The root cause shared by all four affected writers is that "read the current value, then write my delta on top of it" cannot distinguish a value that already reflects the delta from one that does not, no matter how the read is protected. The fix removes the distinction it would need to draw, instead of trying to make it draw it correctly: track, per durable row (the ledger entry; the reservation; the allocation), whether *that specific row's* effect has already been folded into its cache column — and gate every materialization of it, from any caller, on that same per-row check, inside one transaction.

- **`materialize_ledger_entry(p_entry_id)`.** `billing_credit_ledger` gains a nullable `materialized_at timestamptz`. The function locks the one ledger row (`SELECT ... FOR UPDATE`), returns immediately if `materialized_at` is already set, otherwise applies `billing_credit_accounts.posted_credits = posted_credits + credit_delta` for that row's account and sets `materialized_at = now()` on the ledger row — both inside the same transaction. `postLedgerEntry` calls this via `.rpc()` in place of `applyPostedDelta`. Repair no longer recomputes anything: `repair_account_balance`'s ledger half becomes "find this account's ledger rows with `materialized_at IS NULL`, call this same function on each."
- **`materialize_reservation_hold(p_reservation_id)`.** `billing_credit_reservations` gains two nullable markers, `admitted_at` and `hold_released_at`. Locks the one reservation row; if `status = 'active'` and `admitted_at IS NULL`, applies `+reserved_credits` and sets `admitted_at`; if the row is terminal, `admitted_at IS NOT NULL`, and `hold_released_at IS NULL`, applies `-reserved_credits` and sets `hold_released_at`; otherwise no-ops. `claimReservation` and `closeReservation` both call this via `.rpc()` in place of `admitHold`/`releaseHeldCredits`. `repair_account_balance`'s reservation half: find this account's reservations with either marker missing for their current phase, call this same function on each.
- **`materialize_allocation_capacity(p_allocation_id)`.** `billing_credit_allocations` gains a nullable `capacity_materialized_at`. Locks the one allocation row; if it is terminal (`consumed`/`released`) and `capacity_materialized_at IS NULL`, applies the return (`credit_units` minus `consumed_units`, matching `returnToLot`'s existing arithmetic) to `billing_credit_grants.allocated_credit_units` and sets the marker; otherwise no-ops. `settleReservationAllocations`/`releaseReservationAllocations` call this via `.rpc()` in place of `returnToLot`. `repair_lot_allocation` becomes: find this lot's terminal allocations with the marker missing, call this same function on each.

**Why this satisfies the required invariant, rather than merely resembling a fix for it.** Every question of "has this specific effect already happened" is now answered by a single boolean, set transactionally with the effect it describes, read and written under one row lock, by the one function every caller — hot path or repair — invokes to produce that effect. Two invocations for the same row, from any two callers, in any order, serialize on that row's lock: whichever arrives first applies the delta and sets the marker; whichever arrives second sees the marker set and does nothing. There is no longer a "repair path" and a "hot path" as two designs that might disagree about a value in between — there is one path, invoked from two triggers. A writer whose row committed before a repair ran either materializes it itself (if it reaches the function first) or finds it already done (if repair reached the function first) — never both, regardless of timing, because "already done" is read from the same row the write would set it on, inside the same transaction that would set it. This is the invariant required — proven from the primitive's construction, not argued about the design's behavior from outside it.

**Crash safety, unchanged in its reasoning from the prior revision and still true.** Each function's body is one transaction; a crash mid-function rolls back the cache write and the marker together, so there is no partial-materialization state — the row is simply retried, safely, on the next call. This closes the original marker design's two crash windows (A and B, kept below) for a structural reason the marker design never had: the marker and the effect it describes are now set by the *same* statement inside the *same* function, on the *same row* the durable event already lives on (for the ledger and reservation cases) — not two statements on two tables, coordinated only by application-level sequencing.

**No retry loop needed in any of the four converted functions.** Each expresses its cache update as a column-relative `SET col = col + delta` inside a transaction holding the row lock — the relative update PostgREST could never express, now expressed where it can be. `CONTENTION_ATTEMPTS`/`retryDelayMs` are unnecessary here for a structural reason, not a performance one: Postgres serializes concurrent writers to the same row itself, and there is no "lost swap" to retry, because there is no swap — an ordinary `UPDATE ... SET x = x + $1` cannot lose a race the way `UPDATE ... WHERE x = $read_value` can. `CONTENTION_ATTEMPTS` continues to govern the one hot-path writer left unconverted, `takeFromLot`.

**This retracts a specific claim the prior revision made.** "The hot path stays completely unchanged... none of them change here" (the prior revision's §P3 and its bullet in "What this explicitly does not introduce") is false for four of the five writers it named. It survives, exactly as stated, for `takeFromLot` alone. The reason the prior revision believed otherwise: proving "the repair function is internally correct" — atomic, crash-safe by construction — is a different, weaker claim than proving "the repair function cannot be overtaken by an in-flight hot-path writer." The prior revision proved the former and treated it as though it implied the latter.

#### Security model — part of the correctness architecture, not an afterthought

All five functions (`materialize_ledger_entry`, `materialize_reservation_hold`, `materialize_allocation_capacity`, `repair_account_balance`, `repair_lot_allocation`) follow the same profile, matching a precedent this schema already set and then corrected once for exactly this reason: `execution_specs.sql`'s `reject_execution_spec_mutation`, shipped as `SECURITY DEFINER`, then corrected in `execution_spec_guard_security_invoker.sql` after `supabase get_advisors --type security` flagged it as callable by `anon` through `/rest/v1/rpc/reject_execution_spec_mutation` with no reason to be. That precedent is followed here, not reinvented:

- **`SECURITY INVOKER`, stated explicitly rather than left to a default.** The only caller is the service-role client (rule 53), which already has full table access directly — there is no lower-privileged caller these functions exist to grant anything to, so `DEFINER` buys nothing and, per the precedent, is a real cost when it is wrong: a `DEFINER` function reachable by a role that should not have the underlying access is a standing escalation waiting for a future edit to exploit it.
- **`SET search_path = ''`**, with every table reference fully qualified as `public.…` — the same defense against search-path hijacking the precedent already applies.
- **No dynamic SQL.** Every statement in every function body is fixed at definition time; account/lot/entry/reservation/allocation ids are bound parameters, never interpolated into a query string.
- **`REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, then `GRANT EXECUTE ... TO service_role`, explicitly, for all five functions.** Postgres grants `EXECUTE` to `PUBLIC` by default on function creation; left alone, every one of these would be callable over PostgREST's RPC surface by an authenticated or even anonymous browser session — precisely the reachability the precedent's advisor scan exists to catch, on functions that are allowed to move money. None of these five has any business being called by anything other than the service-role client, ever; this is stated as a grant, not inferred from "nobody would call it that way."
- **`supabase get_advisors --type security` run against the migration before it is trusted**, the same verification step that caught the precedent's mistake, named here explicitly so it is not skipped because this document already discusses security in prose.

**A migration is required, precisely scoped.** `CREATE FUNCTION` and the four new nullable marker columns (`materialized_at`, `admitted_at`, `hold_released_at`, `capacity_materialized_at`) are schema, and land through a normal versioned migration in `supabase/migrations/`, exactly as every other schema change in this codebase does. This corrects the prior revision's "no migration required" claim, which conflated "no data migration or backfill" with "no migration at all" — repo architecture is not deployed database architecture until the migration ships. **Whether a data migration is required for the marker columns themselves is a separate question, answered below**, and the prior revision's "no" was premature there too — for reasons the prior revision did not consider, a bare `ADD COLUMN` with no backfill is unsafe.

#### Rollout: migration and mixed-version cutover safety

The steady-state design above (§P3, "The corrected mechanism") is not itself in question here. What is: whether the system can get from today's schema and today's already-running code to that steady state without a window in which `marker IS NULL` is ambiguous — genuinely pending, or already-materialized by a writer that predates the column and has never heard of it.

**R1 — Existing rows must not become indistinguishable from pending ones.** `ADD COLUMN ... materialized_at timestamptz` with no backfill leaves every historical row `NULL` — structurally identical, to any scan that treats `NULL` as "pending," to a row genuinely awaiting materialization. If `repair_account_balance`'s catch-up scan (§P3) runs against an unbackfilled table, it finds *every ledger entry this account has ever posted* "pending" and replays every delta a second time — the exact double-count this document exists to prevent, self-inflicted by the migration.

The fix is not a blanket backfill, because a blanket "mark everything materialized" is a second, opposite hazard: `MaterializationError`'s own existence proves a ledger row can *already* be genuinely unmaterialized in production today — a past `CONTENTION_ATTEMPTS` exhaustion that nobody has repaired, because nothing could. Backfilling *that* row's marker to non-`NULL` would not just fail to fix it — it would make it **permanently unfixable**, forever invisible to the one mechanism now capable of correcting it, while `reconcileBalance` (which recomputes independently of the marker and is unaffected by any of this) keeps reporting the account `consistent: false` on every read, with no path left to close it. This is the concrete failure mode P3's "the drift is permanently invisible" originally described for the crash windows, reappearing at the migration boundary instead of at runtime.

**So the backfill must be preceded by, and conditioned on, the migration's own certification that no such row exists — and "inside its own transaction" is not, by itself, that guarantee.** Under `READ COMMITTED` (the default, and what a migration transaction runs under unless it says otherwise), each statement inside the transaction sees a fresh snapshot as of *that statement*, not one snapshot for the whole transaction. A certification query that reads `billing_credit_accounts` and then, in a second statement, sums `billing_credit_ledger`, admits a writer committing in between: both reads are individually "fresh," but jointly inconsistent — capable of producing either a false-positive abort (a real writer's commit lands between the two reads, and the certification sees drift that is not drift, only a race) or, worse, a false pass that a later step relies on. `READ COMMITTED` alone does not make "inside a transaction" mean "against one closed snapshot."

**Closing that requires explicit locks, acquired before any read, on every table whose concurrent mutation can change either side of a reconciliation equation.** Derived from the actual writer statements, not assumed:

| Table | What concurrently mutates it | Statement type | Table lock mode required |
|---|---|---|---|
| `billing_credit_accounts` | `applyPostedDelta`/`admitHold`/`releaseHeldCredits` (and their `.rpc()` replacements), `ensureCreditAccount` | `UPDATE`, `INSERT` — both take `ROW EXCLUSIVE` | `SHARE` — the weakest mode that conflicts with `ROW EXCLUSIVE`; blocks every writer above while still permitting a concurrent plain `SELECT` (`getBillingBalance`'s read), which observes nothing this certification depends on |
| `billing_credit_grants` | `takeFromLot`/`returnToLot`, lot issuance | `UPDATE`, `INSERT` — `ROW EXCLUSIVE` | `SHARE`, same derivation |
| `billing_credit_ledger` | `postLedgerEntry`'s insert | `INSERT` — `ROW EXCLUSIVE` | `ACCESS EXCLUSIVE` — not a choice: this table gains `materialized_at` in this same migration, and Postgres's `ALTER TABLE ADD COLUMN` itself requires `ACCESS EXCLUSIVE`, held for the rest of the transaction once acquired. `SHARE` would have sufficed for the writer alone; the schema change forces the stronger mode regardless |
| `billing_credit_reservations` | `claimReservation`'s insert, `voidReservation`, `closeReservation`'s status flip | `INSERT`, `UPDATE` — `ROW EXCLUSIVE` | `ACCESS EXCLUSIVE`, same reason — gains `admitted_at`/`hold_released_at` in this migration |
| `billing_credit_allocations` | `allocateReservation`'s batch insert, `settleReservationAllocations`/`releaseReservationAllocations`'s status flip | `INSERT`, `UPDATE` — `ROW EXCLUSIVE` | `ACCESS EXCLUSIVE`, same reason — gains `capacity_materialized_at` in this migration |

The migration acquires all five, explicitly, in a fixed order (`billing_credit_accounts` → `billing_credit_ledger` → `billing_credit_reservations` → `billing_credit_grants` → `billing_credit_allocations` — cache tables and source-of-truth tables interleaved in the order the reconciliation formulas read them), each with `NOWAIT`: `LOCK TABLE billing_credit_accounts IN SHARE MODE NOWAIT;` and so on. **`NOWAIT` is what makes this fail closed** — without it, a lock request that cannot be granted immediately blocks and waits, which is not unsafe but is an operational hang; with it, an unobtainable lock raises immediately, the migration transaction rolls back, and nothing is certified or backfilled. The migration does not proceed on a partial lock set.

A fixed order is a defensive convention here, not a correction to a live deadlock risk: because every hot-path writer issues exactly one statement per PostgREST call (established throughout this ADR), no ordinary application transaction ever holds a lock on one of these five tables while requesting a lock on another — the precondition for a deadlock cycle. The order is still specified explicitly, as asked, rather than left to rely on that argument holding forever.

Only once all five locks are held does the migration:

1. **Certify, in SQL, against the now-closed snapshot:** for every account, `posted_credits`/`reserved_credits` equal the sum `reconcileBalance` would compute from `billing_credit_ledger`/active `billing_credit_reservations`; for every lot, `allocated_credit_units` equals what `reconcileLotAllocation` would compute from `billing_credit_allocations`. Any account or lot that fails aborts the whole migration transaction (`RAISE EXCEPTION`) rather than proceeding around it — there is no automated repairer yet at this point in the rollout, so a failure here is a manual, pre-migration remediation.
   Belt and braces, not a substitute: an operator runs the existing `reconcileBalance`/`reconcileLotAllocation` (via `getBillingBalance` and its lot-level equivalent, unchanged, already deployed) against every account/lot as a pre-migration step, independently of the migration's own in-transaction check. Two independent evaluations of the same already-proven formula, not one trusted blindly.
2. **Backfill every existing row, phase-aware, only after certification passes — still inside the same lock-held transaction:**
   - `billing_credit_ledger.materialized_at`: unconditionally `= created_at` for every existing row. Safe now, and only now, because step 1 just certified there is no row whose delta is genuinely still missing from the cache — every existing ledger row's effect is, by that certification, already correctly reflected in `posted_credits`.
   - `billing_credit_reservations.admitted_at`: `= created_at` for every existing row — `claimReservation` never leaves a row behind whose admit did not resolve one way or the other (a failed admit is synchronously voided in the same call, `store.ts:627-630`), so every row that exists today has a settled admit outcome.
   - `billing_credit_reservations.hold_released_at`: `= COALESCE(settled_at, released_at)` for rows already in a terminal status; `NULL` for rows still `active` — correctly representing that their release has genuinely not happened yet. (A reservation that was voided *before* its admit ever succeeded still gets `admitted_at` backfilled alongside `hold_released_at` here — harmless, not a misrepresentation that matters: both markers land non-`NULL` together, so repair's per-phase check — "is this row's *current* phase pending" — never inspects either value again for a row already fully terminal.)
   - `billing_credit_allocations.capacity_materialized_at`: `= COALESCE(settled_at, released_at)` for `consumed`/`released` rows; `NULL` for `held` rows, correctly still pending a resolution nobody has made yet.

This is "a legacy-safe marker default where only new-protocol writers explicitly create pending rows" (the first candidate design), made precise: the "default" is not a column-level `DEFAULT` clause (which cannot express the phase-conditional, `created_at`/`settled_at`-derived values existing rows need) but an explicit, certified, in-transaction backfill `UPDATE`, gated on the same detectors this ADR already trusts for everything else.

**R2 — A writer on old code, mid-deploy, must not be misread as pending by a newly-active repair.** Vercel deploys roll out incrementally; Vercel Workflows are durable and can span a deploy. Assume — per instruction, not as a convenience — that old-code writers can keep executing for some real window after the schema migration lands, unaware the new columns exist.

Traced precisely, the actual exposure is narrower than "any interaction between old and new code": a specific row's full lifecycle — durable insert *and* materialization attempt — is always handled by exactly one code version, within one request or workflow step; no row is ever partially written by one version and finished by another. Two writers of *different* code versions touching the *same account or lot concurrently, each applying their own distinct delta*, is not a new hazard either: `admitHold`'s own docblock already establishes why (`store.ts:637-663`) — a lost CAS re-reads and retries against whatever the current value is, regardless of *who* changed it. Trace it once for the mixed case to confirm nothing about that argument depended on both sides being old-style CAS: account at 1000; new-code `materialize_ledger_entry` locks the account row, writes `1000 + delta_N = 1050`, commits; old-code `applyPostedDelta`, mid-retry, had read `1000` and attempts `UPDATE ... SET posted_credits = 1000 + delta_O WHERE posted_credits = 1000` — matches zero rows against the current `1050`, the *same* "lost the swap" outcome an old writer produces against any other concurrent writer, old or new — old code retries, reads `1050`, writes `1050 + delta_O`. Final value `1000 + delta_N + delta_O`: correct, no double-count, and nothing added to prove it — it is the existing CAS-retry safety property, which does not care why the value it re-reads changed.

**What old code cannot do safely is be read by repair.** An old-code writer that successfully materializes a row via its own CAS leaves that row's marker `NULL` — old code has no idea the column exists, so it never sets it, even though the effect is already correctly applied. A repair scan that is live during this window and finds that row would read `NULL` exactly as it reads a genuinely-pending new-protocol row, and apply the delta a second time on top of what old code already, correctly, applied. This is the one real gap mixed versions open, and it is entirely about *repair's* read of the marker, never about the hot path's own writes, which compose safely as shown above without any special handling.

**R3 — the exact point after which `NULL` is authoritative.** Repair must not run at all until no old-code writer can still produce a marker-`NULL`-but-already-materialized row. This is not inferred from deploy timing — "the deploy finished" is not evidence every writer that started earlier has finished. It is an explicit, operator-controlled gate, held off until a *mechanical, observable* condition is checked, not assumed.

**Every writer source, enumerated exhaustively.** Rule 24 bounds the enumeration: no cron, scheduler, queue, or background execution technology exists beside Vercel Workflows, so a pre-cutover writer can only be one of two kinds —

1. **An ordinary request or Server Action, non-durable, bounded by the platform's own configured maximum function duration.** A retried client call (network timeout, idempotent replay) is still just another instance of this — bounded the same way, nothing distinct to account for. A CAS loop's own internal retries (`CONTENTION_ATTEMPTS`) run entirely inside one such invocation, already inside this bound.
2. **A Vercel Workflow instance (`operation_runs`, `agent_execution_runs`) that started before the cutover deployment and has not reached a *fully* terminal status.** A platform-level step retry is not a third category — a run mid-retry is, by construction, still non-terminal, already covered here. This category is unbounded in duration by design (that is what "durable" means), so it cannot be waited out on a timer the way category 1 can.

**"Fully terminal," defined to explicitly include the case the obligation names.** `needs_user`/`needs_user_input` is *financially* resolved by P2 (the hold is released) but is **not** execution-terminal: the workflow instance is still alive, still resumable, and a resume (`requeueAnsweredOperation`) re-enters that same instance's code — potentially old code, arbitrarily far in the future, since a founder can take days to answer. Conflating "billing resolved" with "safe to ignore for drain purposes" is exactly the trap this obligation names. So the terminal set used for drain purposes is strictly narrower than P2's own `ACTIVE_STATUSES` narrowing — it excludes `needs_user`/`needs_user_input` explicitly, where P2's billing-authority question already, correctly, does not need to.

**The mechanical condition, both parts required:**

(a) **No in-flight ordinary invocation.** The deployment carrying the `.rpc()`-based writers (§P3, "The corrected mechanism") has been the sole traffic-serving deployment, confirmed via the platform's own deployment status, for at least its configured maximum function duration — checked against the platform's actual promotion timestamp, never against "roughly when the deploy was triggered."

(b) **No non-terminal legacy workflow instance.** A query this product already has the tables to answer directly:
```sql
SELECT id FROM operation_runs
WHERE created_at < :cutover_deployment_at
  AND status NOT IN (<fully terminal statuses — excludes 'needs_user'>);
-- and the equivalent query against agent_execution_runs, excluding 'needs_user_input'
```
returns zero rows. This needs no assumption about whether Vercel Workflows re-pins a resumed step to the deployment active at resume time or keeps it pinned to the one it started under — the condition requires there to be **none left**, which is true regardless of which platform behavior turns out to hold, and is checkable from this application's own state, not from platform introspection this document cannot verify.

**The gate itself.** A server-only environment variable, `BILLING_REPAIR_ENABLED`, read only at the two repair-trigger call sites (`getBillingBalance` and the lot-level equivalent), defaulting unset (repair inert) and stays unset until an operator has independently verified both (a) and (b) above. While unset, those call sites behave exactly as they do today, unchanged: `reconcileBalance`/`reconcileLotAllocation` still run and still log drift; `repair_account_balance`/`repair_lot_allocation` are never invoked — not called-and-skipped, simply never reached, so the guarantee does not depend on a conditional inside the repair path being correct.

- This is the second candidate design (an explicit protocol/version marker), applied narrowly: not a per-row version column — unnecessary, since R2 already shows the hot path needs no version disambiguation, and the only reader that does (repair) needs exactly one global fact ("is it safe to start"), not a fact per row. A per-row version column would answer a question condition (b) above already closes, at the cost of a fifth column and per-row branching everywhere repair reads one.
- **Rollout order, each stage a precondition for the next, not inferred from the others:**
  1. Certification + backfill (R1) — a schema migration, deployed alone, before any application code changes. No app code yet reads or writes the new columns; old code runs entirely unaware of them, exactly as before.
  2. Application deploy: hot-path writers move to the `.rpc()` primitives (§P3); the repair call sites are added, but gated behind `BILLING_REPAIR_ENABLED`, still unset. Safe to roll out incrementally by R2's proof — the only remaining hazard (repair reading a stale-marker row) cannot occur, because repair still never runs.
  3. Drain window: after step 2's deploy is confirmed fully rolled out, verify conditions (a) and (b) above — not assumed from elapsed time alone.
  4. Activation: an operator sets `BILLING_REPAIR_ENABLED`. From this instant, every row with `marker IS NULL` was created after step 1's certification, by code that always sets the marker correctly on materialization — `NULL` is now, and only now, authoritative evidence of a pending effect.

**Rollback.** The migration is purely additive — no existing column, constraint or old-code query is touched, and old code's `.select(...)` calls name their columns explicitly (`store.ts`, `lot-store.ts`, throughout), so old code cannot even see the new ones. Rolling the *application* back to pre-0041 code, with the schema left in place, is therefore safe on its own: old code resumes its original CAS mechanism, indifferent to the migration, and simply stops updating markers on whatever it touches — no corruption, because the old mechanism was never broken, only unaware. The rollback procedure, in order, matching activation's own discipline rather than reversing it carelessly:

1. Set `BILLING_REPAIR_ENABLED` unset/off.
2. **Verify it is off** — read it back; do not treat the write as the guarantee, matching this codebase's general "an independent read, not the write's own response, decides success" discipline.
3. Only then redeploy old application code.
4. **Reactivation is not a resumption of the prior drain proof.** If the system is later forward-rolled again, conditions (a) and (b) are re-verified fresh — old code may have created new non-terminal `operation_runs`/`agent_execution_runs` rows during the rollback window, and a drain proof from before the rollback says nothing about those. There is no partial credit for having drained once.

**Fourth candidate, considered and folded in rather than adopted separately.** "Another mechanism the reservation/allocation lifecycle requires" — yes, but not a fifth design: two-phase entities (admit/release, take/return) need their backfill conditioned on *current status*, not a single unconditional expression the way ledger's one-phase, append-only rows do. That is captured in R1's phase-aware backfill rules above, not a separate mechanism.

**What each of the five required proofs reduces to:**

1. *No historical row replayed merely because the marker is new* — R1's certified, phase-aware backfill, against a snapshot closed by explicit table locks (`SHARE`/`ACCESS EXCLUSIVE`, `NOWAIT`, fixed order) rather than by transaction membership alone; every existing row lands non-`NULL` for every phase it has already resolved.
2. *No old-code writer creates a false pending row during deployment* — impossible by construction: old code never sets the marker, true or false; the risk was always in a *reader* misinterpreting `NULL`, not a writer fabricating a value.
3. *Every genuine crash between fact creation and materialization stays repairable* — unaffected by any of the above; a new-protocol row's marker starts `NULL` exactly as designed, and stays repairable by the steady-state mechanism (§P3, unchanged) once repair is active.
4. *A precise, documented point after which repair may treat the marker as authoritative* — the moment `BILLING_REPAIR_ENABLED` is set, itself gated on both mechanical drain conditions (a) and (b) above — not deploy timing, and not silent about `needs_user`/`needs_user_input` runs still alive at cutover.
5. *Rollback cannot silently corrupt balances* — the migration's additivity, plus the flag-off-verified-then-redeploy ordering, plus reactivation requiring a fresh drain proof rather than reusing an earlier one.

> **The naive design, considered and rejected.** The obvious shape — on drift, recompute the correct total from the ledger (or the allocation rows) and CAS-write that absolute value — is unsafe under the exact conditions that produce the drift in the first place. `CONTENTION_ATTEMPTS` exhaustion happens under sustained *concurrent* contention: several writers hitting the same account or lot at once. If a repairer recomputes the account's total from every committed ledger row while another writer B has committed its own ledger row but not yet won its own cache CAS, the recomputed total already includes B's delta. The repairer's CAS-write succeeds and folds B's delta into the cache early. B's own retry loop then reads the *already-updated* cache, adds its delta again — because nothing told it the cache already reflects it — and posts B's delta twice. The bug is not in the repairer's arithmetic; it is that a full recompute cannot distinguish "already applied by someone else" from "not yet applied," and the codebase's own additive CAS retries (`applyPostedDelta`, `releaseHeldCredits`, `takeFromLot`) have no way to detect that a value they are about to add has already been folded in by an outside actor.
>

> - `billing_credit_ledger` gains a nullable `materialized_at timestamptz`. `applyPostedDelta`/`releaseHeldCredits` set it, in the same call, only on the CAS attempt that actually succeeds.

### P4 — Idempotency must be provable from a row guaranteed to exist for every legitimate outcome, including the zero-credit one

Extends I1 ("charge existence determines financial idempotency... never conflate [it with] whether the hold was closed") with the case I1 did not anticipate: an outcome that legitimately produces no charge at all. `settleReservation`'s existing early-return already contains the right shape for this — it treats an existing charge as authoritative and finishes whatever cleanup the first attempt did not. It is checked *after* trying to find that charge in the ledger, which is exactly wrong for the one outcome that never posts one. The fix: `settleReservation` checks `reservation.status === "settled"` directly, first, independent of any ledger lookup — the reservation row is guaranteed to exist and reach a terminal status for every legitimate settlement, charged or not, and is therefore the correct idempotency key for the case the ledger cannot represent.

## What this explicitly does not introduce

- **No lease, no heartbeat.** A running execution's liveness is Vercel Workflows' problem (ADR 0013); this ADR does not build a second, competing liveness model beside it. P2 asks "has anyone looked at this in longer than its policy allows", never "is the process that owns this still alive."
- **No cron, scheduler, queue, or any background execution beside Vercel Workflows** (rule 24). Every mechanism above fires from a read a caller was already making.
- **No stored procedure or database function for `takeFromLot`.** It is the one hot-path writer that keeps its original CAS-retry shape, for the structural reason given in §P3: its materialization is not preceded by an independent durable row a repair could read separately, so it has no counterpart to be overtaken by. **Revised again**: the prior revision's claim that a function would be "repair-only, never called from a hot-path write" does not survive Obligation 1's proof (§P3). `applyPostedDelta`, `admitHold`, `releaseHeldCredits` and `returnToLot` all move to a function-based primitive (`materialize_ledger_entry`, `materialize_reservation_hold`, `materialize_allocation_capacity`) shared with repair, because the correctness hole is not confined to the repair path — it is the interaction between *any* two callers materializing the same row's effect, one of which happens to be repair. What is still true, and is the actual scope-limiting claim: five named functions, not a general RPC surface, each gated on `EXECUTE` to `service_role` alone (§P3, security model), and none is license to reach for a function the next time a two-table write looks inconvenient elsewhere in this codebase.
- **No relaxed CHECK constraint.** `credit_delta <> 0` stays; P4 does not ask for a zero-delta ledger row.
- **No ledger row for a repair.** A materialization repair moves a cache column back into agreement with the ledger; it is not itself a financial event and must never be recorded as one. `adjustment` (`schema.ts:44`, "a deliberate **manual** correction, always carrying a stated reason") stays reserved for a human-authorized change to the actual balance — a support action, never something this mechanism posts on its own.
- **No new service, and no new module boundary crossed.** Everything above stays inside `src/modules/credits/` and `src/modules/operations/` (ADR 0001).

## Shape of the change

Named so a future implementation sprint has a map, not written here:

| Piece | Where |
|---|---|
| `materialize_ledger_entry(entry_id)`, `materialize_reservation_hold(reservation_id)`, `materialize_allocation_capacity(allocation_id)` — the shared idempotent primitives; `repair_account_balance(account_id)`, `repair_lot_allocation(lot_id)` — thin unmaterialized-row scans over them | new versioned migration (§P3, revised again): `materialized_at`, `admitted_at`, `hold_released_at`, `capacity_materialized_at` — four new nullable marker columns, backfilled for every existing row in the same migration transaction, gated on an in-transaction certification that no account/lot is currently drifted (§P3, Rollout); `SECURITY INVOKER`, fixed `search_path`, `EXECUTE` revoked from `PUBLIC`/`anon`/`authenticated`, granted to `service_role` only |
| `applyPostedDelta`, `admitHold`, `releaseHeldCredits`, `returnToLot` replaced by `.rpc()` calls to the matching primitive; `takeFromLot` unchanged | `credits/store.ts`, `credits/lot-store.ts` |
| Repair trigger at read, calling `repair_account_balance`/`repair_lot_allocation` via `.rpc()`, gated behind `BILLING_REPAIR_ENABLED` (unset by default — §P3, Rollout) | `getBillingBalance` (`service.ts`) and the lot-level equivalent |
| Release-on-pause / re-reserve-on-resume, with the release reason resolved per call site (§P2, revised again) | `pauseOperationForUser`'s two call sites (`business-audit/execution.ts:450` → `cancelled_before_usage`, `agent-execution/execution.ts:1118-1119` → `abandoned_with_usage`) and `requeueAnsweredOperation`'s caller |
| `expireStaleOperation` + the per-operation-type deadline table, scoped to `queued`/`running` only | new module beside `operations/store.ts`, wired into `getOperationStatus` |
| `settleReservation`'s reservation-first idempotency check | `credits/service.ts` |

Withdrawn by this revision: the prior revision's recompute-and-overwrite bodies for `repair_account_balance`/`repair_lot_allocation`, and its claim that no new columns and no migration are needed. Still withdrawn, unchanged by this revision: the `ACTIVE_STATUSES`/`needs_user_input` widening — Obligation 3 answered a different question (what was already spent, not how long to wait) and did not reopen it. Not a reversion to the very first (rejected) marker design: the new marker columns here are safe for the reason given in §P3 — each is set in the same transaction as the effect it describes, on the row that effect already lives on, never coordinated across tables by application-level sequencing, which is exactly the property the original marker design lacked.

## Audit trail

Every automatic action here posts through the existing `recordAuditEvent`, the same convention `credit_charge.settled`/`credit_reservation.released` already use — nothing here invents a second logging path:

- `credit_drift.detected` / `credit_drift.repaired` / `credit_drift.repair_failed` — account or lot id, the drift observed, before/after cache values, and (for `repair_failed`) the constraint the correction would have violated. **Revised again**: `repaired` now records a scan that found and materialized specific unmaterialized rows via the shared primitive (§P3), not an overwrite of a recomputed total; `repair_failed` is unaffected — still the primitive's own `UPDATE` hitting an existing database CHECK constraint.
- `operation.expired_stale` — already the shape `expireStaleAgentExecution`'s own console line follows; made a proper audit event for every operation family rather than a `console.error`. Fires only for `queued`/`running` under the revised P2 — `needs_user`/`needs_user_input` never reach it, because nothing is held to reclaim.
- `credit_reservation.released_for_wait` / re-authorization on resume already posts through the existing `credit_reservation.created` event — no new event type needed for the second half. The release reason recorded (`cancelled_before_usage` or `abandoned_with_usage`, per call site — §P2, Obligation 3) is whatever `releaseOperationBilling` already writes; no new event field needed either.

## Consequences

### Positive

- Closes all four ROADMAP entries. P3's shared primitive proves the required invariant — repair cannot be overtaken by a hot-path write started before it — from its construction (one row, one lock, one idempotency check, one transaction, two callers), not by argument about a design's behavior from outside it. P2's release/re-reserve eliminates the orphaned-hold question for paused operations rather than answering it with a deadline, and Obligation 3 makes explicit, per call site, what was economically at stake before the release.
- No new infrastructure, no new liveness model. The departure from "no database function" is larger than the prior revision claimed — named honestly now, in §P3 — but still five specifically-named functions with no persisted state beyond four nullable markers, not a general RPC surface. `takeFromLot` staying pure CAS is evidence the discipline is not abandoned wholesale, only wherever the proof showed it was actually unsafe.
- The four converted writers lose their retry loops, not only their unsafety. `CONTENTION_ATTEMPTS`/`retryDelayMs` become unnecessary for `applyPostedDelta`, `admitHold`, `releaseHeldCredits`, `returnToLot`'s replacements, because a column-relative `UPDATE` inside a row lock cannot lose the race a value-based CAS can — a genuine simplification the proof forced, not one that was designed in for its own sake.
- Two designs are now named, proven wrong with concrete evidence, and rejected in this document rather than discovered by a future incident or, worse, a production double-charge: the original cross-table marker (both crash windows), and the repair-only function (the concurrent-writer double-count, provable without any crash) — the reasoning is as much the deliverable here as the design is.
- **The rollout itself needs no new infrastructure.** Certification reuses `reconcileBalance`/`reconcileLotAllocation`, already built and already deployed; activation is one environment variable at two call sites, not a feature-flag service, a control table, or a per-row version column — each of those was considered and found to answer a question the staged rollout order already closes.

### Negative / Tradeoffs

- **The rollout is now a four-step operational procedure, not a single deploy.** Certification, migration, a gated application deploy, and an operator-verified activation are each their own precondition for the next; skipping or reordering any one reopens the exact hazard it exists to close (a blanket backfill hides real drift permanently; activating before old code has drained lets repair double-count what old code already applied). This is real operational surface a simpler-looking design would not have needed, and is the direct cost of proving Obligation 4 rather than assuming a deploy is atomic.
- **The shared primitives are now load-bearing for the entire hot path, not only the rare repair path.** A defect in `materialize_ledger_entry` no longer degrades gracefully into "repair occasionally gets it wrong" — it is the only path `posted_credits` ever moves through, so a defect there is a defect in every credit and charge this product processes. This concentrates review risk rather than distributing it: making repair and the hot path share one mechanism is what makes them impossible to disagree, and also what makes a mistake in that one mechanism universal instead of occasional. The security model and pre-trust review named in §P3 carry more weight under this revision than the prior one, not less.
- **An operation that is both last in its own chain and never viewed stays stuck.** P2's staleness trigger (`queued`/`running` only, now that `needs_user` is out of scope) is a read somebody makes. ADR 0037 lets one durable operation enqueue the next, and that enqueue is itself a natural read-trigger for the operation before it — but a chain's *final* operation, if nobody ever opens the page again, has no other caller to notice it. This is a real, bounded gap, not hidden: the honest fix is a genuinely scheduled sweep, which rule 24 reserves for its own ADR, and this document does not claim to close it.
- **Per-operation-type staleness deadlines are a policy decision this ADR does not make.** Narrower now than the first version (only `queued`/`running` need one; `needs_user` no longer does), but the remaining table still needs numbers chosen with the same care `STALE_RUN_GRACE_MS`'s docblock shows (too short fails work a customer paid for, too long costs nothing but time).
- **Re-authorization on resume can fail.** A customer who spends their balance elsewhere while an operation waits on their own answer may return to find resuming refused for insufficient credits — a failure mode the original always-hold design did not have. Named in §P2; the exact user-facing handling is left to the implementing sprint, not invented here.
- **Five functions now need their own review before any of them is trusted with money — three of which sit on the hot path itself.** A function is harder to audit at a glance than a TypeScript CAS loop reviewed the same way every other file in this codebase is; it needs its own focused review (row-locking behaviour, exact idempotency check, what it does under every constraint violation, the security model in §P3) before Sprint C-equivalent work ships it. This is a larger review surface than either prior revision of this ADR asked for, and is the direct cost of the proof Obligation 1 required.
- **This ADR authorizes a shape, not a merge.** Every piece in "Shape of the change" is unimplemented. Rule 14 and the user's own instruction for this document are the same rule: design first, and stop here — three times now, since neither the marker design nor the repair-only function survived its own required proof.
