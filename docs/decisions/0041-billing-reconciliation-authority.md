# 0041 - Billing Reconciliation Authority

Status: Proposed
Date: 2026-08-22
Builds on [0013](0013-durable-operation-execution.md) (durable execution, and rule 24's origin), [0024](0024-vibe-credits-economic-layer.md) (the economic layer this governs)

> **Revision, 2026-08-22, before implementation began.** The P3 mechanism as first written below (`materialized_at`/`capacity_settled_at` markers, set "in the same call" as the aggregate write) contained a real correctness error: the marker and the aggregate live on different tables, so they cannot be set by one PostgREST statement, and the claim that they could was wrong when written, not merely superseded. Re-examination — prompted by an explicit request to prove crash safety, not only concurrent-writer safety, before Sprints B–D began — found the marker design cannot satisfy I5 at all. §P3 below is the corrected mechanism (an atomic, narrowly-scoped repair function, not a marker). §P2 is also revised: `needs_user`/`needs_user_input` are removed from the staleness model entirely, in favor of releasing the hold on entering the wait and re-reserving on resume, which was found to be the actually-correct fix rather than a harder scheduling problem. The original, incorrect P3 text is kept below the corrected version, marked, rather than deleted — see "What P3 originally said, and why it was wrong."

## Context

### What Sprint 0057 already established, and where it stopped

Sprint 0057's corrective work (documented in [the E2b sprint record](../sprints/0057-e2b-ci-postgres-concurrency.md)'s "Verification found two real defects" section) proved a principle this ADR now names and generalizes: **a compare-and-swap on an entity's own terminal-status column is the only authority permitted to finalize the money tied to it.** Two independent implementations already carry it:

- Every deterministic operation family (`business-audit`, `opportunities`, `action-plans`, and the rest) gates its billing calls on `completeOperationRun`/`failOperationRun`'s return value — both are CAS on `operation_runs.status`, both return whether *this call* won the swap, and every caller has always checked it before reaching `settleOperationBilling`/`releaseOperationBilling`. `business-audit/execution.ts:656-682` is the canonical instance: `const transitioned = await completeOperationRun(...); if (!transitioned) return;` — the comment above the charge is explicit: "the charge inherits exactly-once from the state machine rather than needing its own guard."
- Agent execution's two independent finalizers — `finishAgentExecutionStep` (the durable workflow) and `expireStaleAgentExecution` (a request-time backstop) — did **not** check the equivalent boolean until Sprint 0057's corrective commits (`78b1888`, `2d99764`). Before that, both could finalize the same reservation; E2b measured the resulting `charge_without_hold` state 20 times out of 20 under real PostgreSQL MVCC. The fix reused `completeAgentRun`/`failAgentRun` — CAS on `agent_execution_runs.status`, already returning the boolean, simply never checked — rather than inventing anything.

So the *authority* half of the problem — who may act — has one answer, proven twice. What Sprint 0057 deliberately did not solve, and named as out of scope both times, is the four gaps `docs/ROADMAP.md` still lists under "Now — financial correctness":

1. **Drift repair.** `balance.ts`'s `reconcileBalance` and `store.ts`'s `MaterializationError` detect that a materialized cache column has stopped agreeing with the ledger that defines it. Nothing repairs it. `store.ts`'s own comment on `MaterializationError` says so: *"There is no repairer in this codebase — `reconcileBalance` computes drift and nothing acts on it — so the only honest response is to fail loudly."*
2. **Orphaned holds.** `operations/store.ts`'s terminal transitions are reachable only by a live step calling them. A workflow that dies mid-run — the exact failure `expireStaleAgentExecution` was built to answer for agent execution — has no equivalent backstop for any deterministic operation family. `completeOperationRun`/`failOperationRun` are gated on `ACTIVE_STATUSES = ["queued", "running"]` (`store.ts:86`); nothing ever calls them for a run nobody is watching.
3. **Stranded lot capacity.** `lot-store.ts:284`'s `returnToLot` logs and gives up after `CONTENTION_ATTEMPTS` (10) contended writes, on the stated argument that giving capacity back is "the customer-favourable direction" — which is backwards: the customer keeps paying for Credits nothing can spend.
4. **Zero-credit settlement is not idempotent.** `service.ts`'s `settleReservation` finds a retry's existing charge by ledger idempotency key — but `billing_credit_ledger.credit_delta <> 0` is a CHECK constraint (`20260817180000_billing_credits_core.sql:98`), so a zero-credit settlement posts no ledger row at all. A retry finds nothing, falls into `decideSettlement`, sees `reservation.status !== "active"` (already closed by the first attempt), and refuses with `reservation_not_active` — reporting a real success as a failure.

The user's instruction for this document is explicit: analyze these four as one architecture, not four bugfixes, and design the ADR — implementation is separate, later work.

### The precedent that already answers "how, without new infrastructure"

`expireStaleAgentExecution` (`operations/agent-execution/server-writes.ts:279`) already solved "nothing ever comes back to close an abandoned run" for exactly one case, and its own docblock states the doctrine this ADR generalizes:

> "The polling loop terminates every run it is watching. What it cannot do is survive the workflow itself dying... A durable execution that can leave a customer's Credits reserved forever is not one, so there has to be an answer that does not depend on the workflow being alive to give it. This is that answer: a read path notices, and repairs... Because the read is the moment it matters. Somebody is looking at this run's status; the alternative is a cron this product does not have and would need a decision to introduce (rule 24)."

It is fired from `getAgentExecutionStatus`, which the run page already polls. No sweeper, no schedule, no new table — a read chokepoint that already existed, carrying one more check. This is the shape every mechanism below reuses.

### Two detectors already exist and are already unused

`balance.ts`'s `reconcileBalance` and `lots.ts`'s `reconcileLotAllocation` are both pure functions that already compute "what should this cache column read, given the durable rows that define it" — for the account (`posted_credits`/`reserved_credits` vs. the ledger) and for a lot (`allocated_credit_units` vs. its allocation rows), respectively. Both have exactly the callers I1-I3 left them with in Sprint 0057 E1: `reconcileBalance` is called once, by `getBillingBalance`, which logs and returns the drifted figure anyway; `reconcileLotAllocation` has no caller at all. Neither needs to be invented. What is missing is the repair half, and the trigger.

### A gap this analysis found that neither Sprint 0057 nor the ROADMAP names

`operation_runs`'s terminal CAS (`completeOperationRun`/`failOperationRun`) is gated on `ACTIVE_STATUSES = ["queued", "running"]` — it does **not** include `needs_user`, even though `schema.ts`'s `isActive()` counts `needs_user` as active, and its own comment says why: *"A run waiting for an answer still holds..."* its reservation (`schema.ts:248`). An operation paused on a founder's answer that never comes is therefore invisible to the terminal CAS today — there is no path that ever fails it, staleness-aware or not.

Agent execution's own terminal CAS (`failAgentRun`/`completeAgentRun`, `coding-agent/store.ts:680-717`) already includes `needs_user_input` in its gate — so this specific asymmetry is `operation_runs`-only, not systemic. But `expireStaleAgentExecution`'s own eligibility check (`run.status !== "running"`, `server-writes.ts:305`) excludes `needs_user_input` from staleness *declaration* regardless — so a paused-forever agent run is unreachable for a different reason: nothing ever asks whether it should be declared stale. Both families therefore share the same live gap at the staleness-declaration layer, for a structurally different reason at the authority layer. Any design that only widens `expireStaleAgentExecution`'s pattern without addressing this is incomplete, and is treated as such below.

## Decision

Every one of the four gaps is one of exactly two questions — **who may act**, and **what is the durably correct value** — and both questions already have one answer apiece, proven or half-built. This ADR is four applications of two mechanisms, not four designs.

### P1 — Terminal-transition CAS is the only billing authority (doctrine, now named rather than emergent)

Restated as a standing rule rather than a pattern that happens to appear twice: **any entity that can independently trigger settlement or release of Credits must expose a CAS on its own terminal-status column, and every caller of a billing-affecting transition must check the boolean it returns before touching money.** `operation_runs.status` and `agent_execution_runs.status` are the two existing instances; a future billable entity (a third finalizer, a new execution surface) inherits this by doctrine, not by copying code.

**P1 needs no correction.** The needs-`needs_user`-widening this section originally required is withdrawn — see the revised P2 below, which removes the reason for it.

### P2 — Staleness is declared only at a read that already exists, never on a schedule; `needs_user` is not staleness at all

**Revised.** The first version of this section tried to fold `needs_user`/`needs_user_input` into the same staleness-deadline model as a dead workflow, and required widening `operation_runs.ACTIVE_STATUSES` and `agent_execution_runs`'s eligibility to reach it. Re-examined: that both requires guessing a policy that is genuinely hard to calibrate (how long is too long to wait for a founder to answer a question — too short interrupts a real answer, too long defeats the point) and treats the wrong symptom. The actual question is not "when has a human waited too long" — it is "why is money held reserved at all while nothing is running."

**It should not be.** A reservation exists under §18/§55's "money before work" principle to guarantee capacity for work about to happen. While an operation sits in `needs_user`/`needs_user_input`, no provider call is in flight, nothing is being spent, and nothing is at risk of being raced away by another operation — the premise that justified taking the hold does not hold during the wait. `pauseOperationForUser` (`operations/store.ts:335`) and its agent-execution equivalent, checked directly: **neither releases the reservation today.** `business-audit/execution.ts:450` and `agent-execution/execution.ts:1118-1119` both call `pauseAuditForQuestion`/`pauseAgentRunForUser` and `pauseOperationForUser` with no billing call anywhere near either site — this is a real, previously unnamed gap, not a hypothetical.

**The fix:** release the hold at the same moment the operation enters the wait state, and re-authorize (fresh `authorizeOperationCredits`/`holdAgentExecutionCredits` call, re-pricing from whatever policy is current, exactly as a brand-new operation would) at the moment it resumes (`requeueAnsweredOperation`). This is not a new mechanism — it is the *existing* release/reserve primitives, called at two points that do not call them today. It eliminates the orphaned-hold question for this state entirely rather than answering it: an operation abandoned in `needs_user` forever now holds **nothing**, so there is nothing to reclaim, no deadline to calibrate, and no staleness declaration ever needed for this state. `ACTIVE_STATUSES`/`agent_execution_runs`'s eligibility do not need widening, because by the time either state is reached, its billing is already fully resolved.

**The cost, named rather than hidden:** re-authorization on resume can fail — the customer may have spent the reserved balance elsewhere while waiting. This is a real, new failure mode the original design (hold forever) did not have, and needs its own product-level answer (most likely: fail the operation with a distinct, clear failure code — "insufficient credits to resume" — rather than the generic staleness code this ADR otherwise uses). That is a small, well-scoped decision for the sprint that implements this, not a design gap this document leaves open.

**What P2 keeps from the original design, unchanged:** for `queued`/`running` — a workflow that is genuinely dead, not paused — the read-triggered generalization of `expireStaleAgentExecution` stands as originally proposed: a shared `expireStaleOperation`, wired into `getOperationStatus` the way `expireStaleAgentExecution` is wired into `getAgentExecutionStatus`, governed by a per-operation-type deadline table (never one constant, for the reason `AGENT_SANDBOX_LIFETIME_MS` is specific to agent execution's own sandbox bound), calling the existing terminal CAS and reporting nothing expired on a lost swap. Explicitly out of scope, restated: whether an operation abandoned in `needs_user` forever should eventually be cleaned up for non-financial reasons (stale UI state, operator hygiene) is a real question and is not this ADR's — nothing is financially at stake once the hold is released, and "Now — financial correctness" is the only thing this document governs.

### P3 — An atomic, narrowly-scoped repair function — not a marker

**Revised. The marker design below (kept, marked, as the record of what was first proposed) does not work, and the error was found before any migration was written, which is exactly why this document asked to stop there.**

**The hole, proven.** `materialized_at` was proposed on `billing_credit_ledger`; the aggregate it marks lives on `billing_credit_accounts` — a different table, a different row. PostgREST issues one statement per call; there is no statement that updates both atomically. The claim that `applyPostedDelta`'s "existing successful UPDATE just adds `materialized_at = now()` to a patch it already sends" is false as written — that UPDATE targets `billing_credit_accounts`, and `materialized_at` lives on a row in `billing_credit_ledger` that update never touches. Setting them requires two separate statements, and two separate statements admit a crash between them:

- **(A) aggregate updated, crash before the marker.** The account's `posted_credits` already reflects the delta; the ledger row still reads `materialized_at IS NULL`. A later repair, trusting the marker, finds this row "pending," replays its delta, and applies it a **second** time. I5 ("at most once, ever") fails.
- **(B) marker updated, crash before the aggregate.** The ledger row now reads "materialized"; `posted_credits` never moved. A later repair scan finds no pending rows for this account and does nothing — the drift is **permanently invisible** to the mechanism built to find it. Worse than the status quo, which at least throws.

Both windows are real under the exact architecture this codebase already uses (PostgREST, single-statement writes, no cross-table transaction from the application layer), and no choice of *which* table the marker lives on closes them, because the two facts being recorded are irreducibly on two different tables. The design did not merely need a smaller tweak; it needed to not exist.

**What was considered instead, and why each was accepted or rejected:**

- *Recompute the aggregate and overwrite it.* Already rejected in the first version of this ADR — unsafe under concurrent in-flight writers (a repairer's recompute silently folds in another writer's not-yet-applied delta, which that writer then re-applies on top). Still rejected; restated for completeness.
- *A ledger sequence/cursor.* `billing_credit_ledger.id`/`billing_credit_allocations.id` are `uuid default gen_random_uuid()` (`20260817180000_billing_credits_core.sql:91`; `20260818120000_billing_credits_stripe_entitlements.sql:206`) — unordered, so a cursor needs a *second* new sequence column before it can mean anything. For the ledger case, the cursor *can* be co-located on the same row as the aggregate it advances (`billing_credit_accounts` carries both `posted_credits` and the cursor, so one statement moves both — genuinely atomic, no crash window). For allocations the trick does not transfer: what needs recording is the *resolution* of an allocation (an `UPDATE`, not its creation), and Postgres has no client-visible way to stamp an update-time sequence value without either a trigger or a function — which is exactly the category this option was trying to avoid. Rejected as the general mechanism: it solves the ledger side alone, at the cost of a second coordinated column, and does not generalize.
- *A dedicated repair/debt table.* The closest alternative to a real fix, and still unsafe for the same root reason: recording a debt row *reactively*, after `CONTENTION_ATTEMPTS` exhausts, reopens the crash window (a process that dies before the debt row exists leaves no trace); recording it *eagerly*, before every attempt, closes the window but adds a network round-trip to every billing write for a table that is empty in the common case. Rejected as the mechanical fix. Its genuinely useful half — an audited trail for a human to read — is served by something that already exists (§ Audit trail, unchanged) rather than a new stateful table.
- *Version markers.* Not a distinct alternative for this problem — a `version`/optimistic-lock column restates the guard `applyPostedDelta`/`takeFromLot` already provide via value-based CAS (`.eq("posted_credits", read_value)` already *is* an optimistic version check). It does not answer "which rows are still pending," which is the actual gap. Noted, not adopted, because there is nothing here to adopt.
- *Eliminate the materialized-cache model.* Rejected outright, for both tables, for the same reason: the cache is not a read-performance convenience here, it is the atomicity primitive that makes `admitHold`/`takeFromLot`'s admission checks safe at all — "a sum over history cannot be locked" (`store.ts`'s own words). Recomputing from the ledger on every admission check would remove the one thing that makes concurrent admission safe.
- *Operator-only repair under quiescence.* Correctly conservative — no automated write ever risks a mistake — but does not close the gap this ADR exists to close: it is louder logging, not a repair, and still needs *some* mechanism to actually apply a correction whenever a human does act, which reduces to one of the options above.
- *A transactional Postgres function (RPC), narrowly scoped.* **Adopted**, reasoned below.

**Why a function closes both windows, and why it is safe to adopt here without eroding the discipline that rejected one before.** The double-counting failure in every non-transactional design above has one root cause: reading the ledger and writing the cache are two separate statements, so another transaction can commit between them. A PL/pgSQL function invoked through PostgREST's `.rpc()` executes as **one** transaction: it can `SELECT ... FOR UPDATE` the account (or lot) row first, taking a row lock that blocks every other writer targeting that same row — including the ordinary CAS writers, which simply queue behind the lock and proceed normally once it releases, reading whatever the function just corrected and adding their own delta on top exactly as they already do when racing an ordinary writer — then recompute the expected total from the ledger (or allocation rows), write it, and commit. Nothing can observe or interleave with a half-done state, because there is no such state: either the whole transaction commits or none of it does, which is what "crash safety" means. This needs no marker, no migration, no backfill, and no drift-audit-before-migration risk, because there is no persisted "pending" state for a crash to catch mid-flight.

This reopens something the first version of this ADR closed on principle — "no RPC or stored procedure ... the first RPC in this schema beyond triggers." That principle held for the hot path, where PostgREST's single-statement limitation is a *design constraint the application works within*, proven sufficient by every CAS loop Sprint 0057 already validated. It does not hold here, because the problem is not "PostgREST cannot express a relative update" (solved, by CAS, everywhere else) — it is "no application-level sequence of separate statements can be made atomic," which is a different, stronger claim, and no column layout changes that. The function is adopted **narrowly**: it is called only from the rare repair path (§ triggers, below), never from `applyPostedDelta`/`releaseHeldCredits`/`takeFromLot`/`returnToLot`'s ordinary hot-path writes, which are untouched by this revision and keep exactly the CAS shape Sprint 0057 already proved. One repair-only function per cache (`repair_account_balance(account_id)`, `repair_lot_allocation(lot_id)`) — not a general-purpose RPC surface, not a replacement for the CAS discipline everywhere else, and not license to reach for a function the next time a two-table write looks inconvenient.

**Trigger and lifecycle, revised.** `getBillingBalance` (and the equivalent lot-level read) calls `reconcileBalance`/`reconcileLotAllocation` exactly as today; on `consistent: false`, it calls the repair function for that account/lot instead of only logging. The function is idempotent by construction — invoked against an account with no drift, it recomputes the same value already there and either no-ops or writes a value equal to what was read, which is harmless either way. This collapses the five-state lifecycle the user asked for into three, honestly: `credit_drift.detected` (the existing pure detector fires), `credit_drift.repaired` (the function's transaction committed a correction), `credit_drift.repair_failed` (the function's own `UPDATE` hit an existing database CHECK constraint — e.g. `available_non_negative` — meaning the drift is not a simple lag but something structurally unsafe to auto-correct; this is the new home for "unexplained," bounded by constraints the database already enforces rather than by an ad hoc judgment call in application code). All three post through the existing `audit_events` mechanism (§ Audit trail), unchanged from the first version of this ADR.

**No migration required for this design.** No new columns, no backfill, no pre-migration drift audit — the function reads current, live rows every time it runs; it has no persisted state of its own to get out of sync with anything. This removes Sprint B's entire "migration safety" burden from the roadmap, at the cost of introducing the function itself, which needs its own review before it is trusted with money (§ implementation plan revision).

> **The naive design, considered and rejected.** The obvious shape — on drift, recompute the correct total from the ledger (or the allocation rows) and CAS-write that absolute value — is unsafe under the exact conditions that produce the drift in the first place. `CONTENTION_ATTEMPTS` exhaustion happens under sustained *concurrent* contention: several writers hitting the same account or lot at once. If a repairer recomputes the account's total from every committed ledger row while another writer B has committed its own ledger row but not yet won its own cache CAS, the recomputed total already includes B's delta. The repairer's CAS-write succeeds and folds B's delta into the cache early. B's own retry loop then reads the *already-updated* cache, adds its delta again — because nothing told it the cache already reflects it — and posts B's delta twice. The bug is not in the repairer's arithmetic; it is that a full recompute cannot distinguish "already applied by someone else" from "not yet applied," and the codebase's own additive CAS retries (`applyPostedDelta`, `releaseHeldCredits`, `takeFromLot`) have no way to detect that a value they are about to add has already been folded in by an outside actor.
>
> **The design this ADR specifies instead.** Every write that moves a durable, authoritative row *and* a derived cache column already writes the durable row first (`postLedgerEntry` before `applyPostedDelta`; the allocation status flip in `settleReservationAllocations`/`releaseReservationAllocations` before `returnToLot`). What is missing is a durable marker, on the authoritative row itself, recording whether its effect has been folded into the cache yet:
>
> - `billing_credit_ledger` gains a nullable `materialized_at timestamptz`. `applyPostedDelta`/`releaseHeldCredits` set it, in the same call, only on the CAS attempt that actually succeeds.
> - `billing_credit_allocations` gains a nullable `capacity_settled_at timestamptz` (or equivalent), set by `returnToLot`'s caller only when that specific return succeeds.
>
> **This claim — "in the same call" — is the error this revision found.** The marker and the aggregate are on different tables; no single call sets both. Everything built on that claim below it (the replay design, the migration/backfill plan) inherited the error and is superseded by the corrected §P3 above.

### P4 — Idempotency must be provable from a row guaranteed to exist for every legitimate outcome, including the zero-credit one

Extends I1 ("charge existence determines financial idempotency... never conflate [it with] whether the hold was closed") with the case I1 did not anticipate: an outcome that legitimately produces no charge at all. `settleReservation`'s existing early-return already contains the right shape for this — it treats an existing charge as authoritative and finishes whatever cleanup the first attempt did not. It is checked *after* trying to find that charge in the ledger, which is exactly wrong for the one outcome that never posts one. The fix: `settleReservation` checks `reservation.status === "settled"` directly, first, independent of any ledger lookup — the reservation row is guaranteed to exist and reach a terminal status for every legitimate settlement, charged or not, and is therefore the correct idempotency key for the case the ledger cannot represent.

## What this explicitly does not introduce

- **No lease, no heartbeat.** A running execution's liveness is Vercel Workflows' problem (ADR 0013); this ADR does not build a second, competing liveness model beside it. P2 asks "has anyone looked at this in longer than its policy allows", never "is the process that owns this still alive."
- **No cron, scheduler, queue, or any background execution beside Vercel Workflows** (rule 24). Every mechanism above fires from a read a caller was already making.
- **No stored procedure or database function *on the hot path*.** Every CAS in `applyPostedDelta`, `releaseHeldCredits`, `takeFromLot`, `returnToLot` and every other ordinary billing write exists specifically *because* PostgREST cannot express a column-relative update — the comments in `store.ts`, `lot-store.ts` and `contention.ts` all say so independently — and none of them change here. **Revised**, narrowly: P3's repair mechanism *does* use one function per cache (§P3), because the correctness hole it closes — atomicity across two tables, provably unreachable by any sequence of separate PostgREST statements — is a different and stronger problem than "PostgREST cannot express a relative update," which CAS already solves everywhere else. The function is repair-only, never called from a hot-path write, and is not license to reach for one elsewhere.
- **No relaxed CHECK constraint.** `credit_delta <> 0` stays; P4 does not ask for a zero-delta ledger row.
- **No ledger row for a repair.** A materialization repair moves a cache column back into agreement with the ledger; it is not itself a financial event and must never be recorded as one. `adjustment` (`schema.ts:44`, "a deliberate **manual** correction, always carrying a stated reason") stays reserved for a human-authorized change to the actual balance — a support action, never something this mechanism posts on its own.
- **No new service, and no new module boundary crossed.** Everything above stays inside `src/modules/credits/` and `src/modules/operations/` (ADR 0001).

## Shape of the change

Named so a future implementation sprint has a map, not written here:

| Piece | Where |
|---|---|
| `repair_account_balance(account_id)`, `repair_lot_allocation(lot_id)` — transactional functions, no new columns | new migration; no backfill, no pre-migration drift audit required (§P3, revised) |
| Repair trigger at read, calling the functions via `.rpc()` | `getBillingBalance` (`service.ts`) and the lot-level equivalent |
| Release-on-pause / re-reserve-on-resume (§P2, revised) | `pauseOperationForUser`'s two call sites (`business-audit/execution.ts:450`, `agent-execution/execution.ts:1118-1119`) and `requeueAnsweredOperation`'s caller |
| `expireStaleOperation` + the per-operation-type deadline table, scoped to `queued`/`running` only | new module beside `operations/store.ts`, wired into `getOperationStatus` |
| `settleReservation`'s reservation-first idempotency check | `credits/service.ts` |

Withdrawn by the revision: the `materialized_at`/`capacity_settled_at` columns and their migration/backfill, and the `ACTIVE_STATUSES`/`needs_user_input` widening — neither is needed under the corrected design.

## Audit trail

Every automatic action here posts through the existing `recordAuditEvent`, the same convention `credit_charge.settled`/`credit_reservation.released` already use — nothing here invents a second logging path:

- `credit_drift.detected` / `credit_drift.repaired` / `credit_drift.repair_failed` — account or lot id, the drift observed, before/after cache values, and (for `repair_failed`) the constraint the correction would have violated (§P3, revised).
- `operation.expired_stale` — already the shape `expireStaleAgentExecution`'s own console line follows; made a proper audit event for every operation family rather than a `console.error`. Fires only for `queued`/`running` under the revised P2 — `needs_user`/`needs_user_input` never reach it, because nothing is held to reclaim.
- `credit_reservation.released_for_wait` / re-authorization on resume already posts through the existing `credit_reservation.created` event — no new event type needed for the second half.

## Consequences

### Positive

- Closes all four ROADMAP entries. P3's repair function proves crash safety directly (one transaction, no persisted intermediate state) rather than by argument about a design that could not actually deliver it. P2's release/re-reserve eliminates the orphaned-hold question for paused operations rather than answering it with a deadline.
- No new infrastructure, no new liveness model. The one departure from "no database function" is named, scoped to two repair-only functions, and does not touch the CAS discipline every hot-path billing write still follows unchanged.
- The unsafe marker version of P3 is named, proven wrong with both crash windows, and rejected in this document rather than discovered by a future incident or, worse, by a production double-charge — the reasoning is the deliverable as much as the design is.

### Negative / Tradeoffs

- **An operation that is both last in its own chain and never viewed stays stuck.** P2's staleness trigger (`queued`/`running` only, now that `needs_user` is out of scope) is a read somebody makes. ADR 0037 lets one durable operation enqueue the next, and that enqueue is itself a natural read-trigger for the operation before it — but a chain's *final* operation, if nobody ever opens the page again, has no other caller to notice it. This is a real, bounded gap, not hidden: the honest fix is a genuinely scheduled sweep, which rule 24 reserves for its own ADR, and this document does not claim to close it.
- **Per-operation-type staleness deadlines are a policy decision this ADR does not make.** Narrower now than the first version (only `queued`/`running` need one; `needs_user` no longer does), but the remaining table still needs numbers chosen with the same care `STALE_RUN_GRACE_MS`'s docblock shows (too short fails work a customer paid for, too long costs nothing but time).
- **Re-authorization on resume can fail.** A customer who spends their balance elsewhere while an operation waits on their own answer may return to find resuming refused for insufficient credits — a failure mode the original always-hold design did not have. Named in §P2; the exact user-facing handling is left to the implementing sprint, not invented here.
- **Two functions now need their own review before they are trusted with money.** A function is harder to audit at a glance than a TypeScript CAS loop reviewed the same way every other file in this codebase is — it needs its own focused review (row-locking behaviour, exact recompute logic, what it does under every constraint violation) before Sprint C-equivalent work ships it, which the marker design would not have required (at the cost of not actually working).
- **This ADR authorizes a shape, not a merge.** Every piece in "Shape of the change" is unimplemented. Rule 14 and the user's own instruction for this document are the same rule: design first, and stop here — twice now, since the first design did not survive its own crash-safety check.
